## Context

The frontend is a single Vite project (`frontend/`) with one HTML entry (`index.html` → `src/main.tsx` → `App.tsx`) and no router — `App.tsx` currently switches between Manual Assignment and Day Planning via a local `view` state with a shared header/nav (see `frontend/src/App.tsx`). The backend (`backend/app/main.py`) exposes `GET /employees`, `GET /service-visits`, `GET /assignments`, `POST /assignments`; all six entities already have complete Pydantic output schemas in `backend/app/schemas.py` (`RegionOut`, `SkillOut`, `CustomerOut`, `CustomerLocationOut`, `ContractOut`, `EmployeeOut`) with nested relationships already modeled (e.g. `CustomerLocationOut.customer`/`.region`, `ContractOut.customer_location`/`.required_skills`), so no new schemas are needed — only new routes. See proposal.md - Why / What Changes for motivation and scope; see specs/customer-portal/spec.md for the required behavior.

## Goals / Non-Goals

**Goals:**
- Give the Customer Portal a genuinely separate top-level experience (no shared header/nav with Planning) without adding a routing library or a second deployable frontend project, per the confirmed "same frontend project, distinct top-level area" scope.
- Add only the backend read endpoints needed to expose the three entities with no standalone list endpoint today (Customers, Customer Locations, Contracts) plus Regions and Skills, reusing existing schemas and eager-loading patterns already used in `main.py`.

**Non-Goals:**
- No pagination, search, or filtering within the Customer Portal — six small, demo-scale entity lists are within what a single unfiltered list view can reasonably show; can be added later if data volume grows.
- No live refresh/polling — the portal loads its data once per page load (consistent with how the Planning app already works); a stale view is refreshed by reloading the page.
- No authentication, editing, or role model — per proposal.md, explicitly deferred.

## Decisions

- **Vite multi-page entry, not a router.** Add a second static HTML entry point, `frontend/customer-portal.html`, mounting a separate React tree from `frontend/src/customer-portal/main.tsx` (its own `CustomerPortalApp` root), alongside the existing `index.html` → `App.tsx` (Planning). Register both entries in `vite.config.ts` under `build.rollupOptions.input` so `npm run build` emits both pages. This gives two genuinely separate top-level pages (no shared DOM, header, or component tree) inside one Vite project/dev server/`package.json`, without introducing `react-router` or a second deployable app. Alternative considered: `react-router` with a top-level route split — rejected as an unnecessary new dependency for two pages that don't need client-side navigation between them; a full page load between Planning and the Portal is an acceptable trade for "clearly separate."
- **A plain link from the Planning header to the Portal is the landing entry point.** `App.tsx`'s header gets one additional `<a href="/customer-portal.html">Customer Portal</a>`. This satisfies "reachable via a landing entry point distinct from Planning's own navigation" — it's a doorway into the portal, not shared navigation rendered inside the portal itself (the spec's read-only requirement is about what's visible *inside* the portal, not how a user gets there).
- **Client-side relationship computation over one all-in-one fetch, matching the existing Planning app's pattern.** `CustomerPortalApp` fetches all six lists once (`employees`, `customers`, `customer-locations`, `contracts`, `regions`, `skills`) in parallel on mount, mirroring `App.tsx`'s existing `Promise.all` load. Each entity's detail view computes its relationships (e.g. a Region's Employees and Customer Locations) by filtering the other already-loaded lists on the relevant foreign-key id already present in the nested objects (e.g. `employee.regions[].id`, `customerLocation.region.id`) — no new relationship-specific backend endpoints. Alternative considered: bespoke `/regions/{id}` "detail with relations" endpoints per entity — rejected as unnecessary backend surface when the full dataset is already small enough to load once and cross-reference client-side.
- **One view component per entity, sharing small presentational primitives**, not one fully generic "entity framework" component. Six small view components (`EmployeesView`, `CustomersView`, `CustomerLocationsView`, `ContractsView`, `SkillsView`, `RegionsView`), each owning its own list/detail toggle and its own relationship-rendering logic, sharing a plain `ListTable` and `DetailField` presentational component for consistent look. Alternative considered: one generic entity browser parameterized by a relationship-config object for all six entities — rejected as premature abstraction; the six entities' relationship shapes are different enough (1–3 related lists each, different fields) that a generic config would end up about as complex as six small components, for less clarity.
- **Master–detail within each entity view**: selecting a list row swaps that entity's panel from list to detail (with a "back to list" control), rather than a split pane. Simplest layout that stays "simple, clean, suitable for business users."
- **Backend**: add `GET /regions`, `GET /skills`, `GET /customers`, `GET /customer-locations`, `GET /contracts` to `backend/app/main.py`, each ordered by `id` and using the same `joinedload` pattern already used for `list_employees`/`list_service_visits`/`list_assignments`, returning the existing `RegionOut`/`SkillOut`/`CustomerOut`/`CustomerLocationOut`/`ContractOut` schemas unchanged.

## Risks / Trade-offs

- [Six unfiltered list endpoints/views have no pagination] → Acceptable at current seed/demo data scale, consistent with the rest of the app today; revisit if a real customer's data volume grows.
- [Client-side relationship computation across six separately-fetched lists has no live-consistency guarantee — a change made elsewhere doesn't appear until the portal page is reloaded] → Acceptable: the portal is a single-snapshot read view per page load; no polling/live-sync is in scope for this change (see Non-Goals).
- [A second Vite HTML entry point needs an explicit `rollupOptions.input` update, otherwise `npm run build` silently keeps producing only `index.html`] → Caught in tasks.md as its own verification step (build both pages and confirm both are emitted).
