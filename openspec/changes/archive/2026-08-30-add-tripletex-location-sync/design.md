## Context

`backend/app/tripletex.py` already has the full pattern this reuses: `TripletexClient.get_customers()` paginates a Tripletex list endpoint, `_apply_fields()` diffs a `_SCALAR_FIELD_MAP` of Tripletex-key → local-attribute pairs, and `sync_customers()` reconciles create/update/soft-delete/restore with a single commit. `CustomerLocation` (`backend/app/models.py`) is currently pure local fixture data: autoincrement `id`, required `region_id`, a single `address: str`, and required `latitude`/`longitude` — none of it sourced from anywhere external. Region assignment is planned to move to a GPS/geofence-based lookup against region masterdata in a later change; this change only needs to keep `region_id` present on the table without inventing that lookup now.

Confirmed via live calls against the connected Tripletex account (see proposal.md - Why): `GET /deliveryAddress` is a real, working, paginated endpoint returning the same underlying address records visible elsewhere in the account (`addressLine1`, `addressLine2`, `postalCode`, `city`, `country`, `displayName`, `addressAsString`, `name`, and a `customerVendor` reference, fetched with `?fields=customerVendor(*)` field expansion to confirm it resolves to a real linked company rather than an unexpanded reference). Customer↔delivery-address links are now configured in the account: 9 delivery addresses across 4 customers, several customers with more than one — confirming the "a customer can have multiple locations" requirement is exercised by real data, not just seed fixtures. The full delivery address record was also checked field-by-field for anything GPS-shaped: it has none — only `knr`/`gnr`/`bnr`/`fnr`/`snr`, Norwegian cadastral (property registry) numbers, not coordinates — confirming geocoding is genuinely required rather than redundant with data Tripletex already provides.

## Goals / Non-Goals

**Goals:**
- Reuse the customer sync's reconciliation shape exactly (create/update/soft-delete/restore keyed by Tripletex id) rather than inventing a new pattern.
- Keep the Customer Portal and every other consumer of `CustomerLocationOut` working by preserving the existing `address: str` field's meaning (a single display string), even though the location is now built from several structured Tripletex fields. This doesn't mean zero frontend changes, though — see the region/coordinates nullability decision below and proposal.md - Impact.

**Non-Goals:**
- No automatic region assignment for synced locations. Region assignment is planned to become GPS/geofence-based against region masterdata in a later change; until then, `region_id` is a local-only field this sync never touches, and the seed script is the only thing that fills it in (for demo purposes).
- No UI for manually editing a customer location's region or coordinates if sync/geocoding produces a wrong or missing result — out of scope; the existing Customer Portal is read-only and stays that way.
- No attempt to reconcile the mismatch between this Tripletex account's real-world addresses (Norwegian) and the app's existing demo employee/region fixtures (Dutch cities) — see Risks.

## Decisions

- **Sync source is `GET /deliveryAddress`, filtered to records with `customerVendor` set.** A delivery address without a linked customer is skipped entirely (never becomes a customer location, never counts toward "removed" either, since it was never eligible). Alternative considered: use each customer's own `physicalAddress` (always populated, one per customer) instead — rejected per the user's explicit choice to link real delivery addresses in Tripletex rather than collapse to one location per customer.
- **Customer location sync runs after customer sync, in the same places: backend startup and the existing `POST /customers/sync` endpoint.** It needs customer sync to have already run in the same pass so `customerVendor.id` resolves against locally-known customers; a delivery address whose linked customer isn't known locally (shouldn't normally happen given customer sync just ran first, but is possible if Tripletex data is inconsistent) is treated the same as "no linked customer" — skipped, not an error. No new endpoint or frontend button — mirrors "sync ... when pressing sync button" using the button that already exists, since the Customer Portal's refresh flow already re-fetches customer locations afterward regardless of what triggered the backend-side sync.
- **`id` becomes Tripletex-owned, matching the customer-id migration's precedent exactly.** `CustomerLocation.id` switches from autoincrement to Tripletex's own delivery-address id, non-autoincrement. Since `contracts.customer_location_id` is a hard FK dependency, this requires the same kind of migration as `0004_tripletex_customers.py`: truncate `customer_locations` cascading into `contracts`, `service_visits`, and `assignments`, then drop the old serial default. This is disruptive to any locally-created demo data exactly the way the original customer migration was, and is called out the same way.
- **`region_id` becomes nullable, and sync never sets or changes it.** Region assignment is explicitly deferred to a later change that will derive it from the location's coordinates against geofenced region masterdata — building a city-name-based stand-in now would just be thrown away, and the user asked specifically to keep region "connected to customer location in some way" without inventing that derivation logic yet. `sync_customer_locations` reconciles every Tripletex-sourced field but leaves `region_id` alone entirely, on create and on update alike — a location keeps whatever region it had (or has none) across every re-sync. Alternative considered: derive a region from the location's city (e.g. `_get_or_create(Region, city)`), the originally-planned approach — superseded per this feedback in favor of waiting for the real geofencing mechanism.
- **Seed data assigns regions itself, since sync won't.** `backend/app/seed.py` assigns a region to every location it uses for demo contracts, reusing the current seed file's existing per-location region choices (north_holland, utrecht, south_holland, south_holland, in that order) for as many locations as that list covers, and a random existing region for any additional location beyond it — Tripletex may now return a different number of locations than the seed file was originally written for (9 in the connected account today, vs. 4 original fixtures). This is a seed-only concern: production sync behavior is unaffected, and a location outside of seeding simply has no region until the future geofencing feature (or a human, once that capability exists) assigns one.
- **Coordinates are geocoded with `geopy` against OpenStreetMap's Nominatim service** (both open-source; `geopy` is MIT-licensed). Nominatim's usage policy requires a custom `User-Agent` and at most one request per second; `geopy.extra.rate_limiter.RateLimiter` enforces that automatically. Geocoding runs only when a location is new or its address fields changed since the last sync (checked the same way `_apply_fields` already detects a changed field), so a full re-sync of unchanged addresses costs zero geocoding requests. `latitude`/`longitude` become nullable to represent "not yet resolved" (new address, or the geocoder found nothing / errored) rather than defaulting to a wrong value like `0, 0`.
- **A visit at a location with unresolved coordinates, or with no assigned region, is excluded from the optimizer, not blocked from being manually assigned.** Manual assignment doesn't use a visit's coordinates or region for any validation today, so nothing changes there; both exclusions are scoped to `build_optimize_payload`, mirroring the existing past-date exclusion pattern (a visit the solver never even sees, reported unscheduled). The region exclusion exists because the solver's region hard constraint has no way to match an employee against a `None` region — rather than let that surface as a confusing permanent violation, the visit is treated as not yet ready to schedule, the same as an ungeocoded one.
- **No re-geocoding retry policy beyond "try again next sync."** If geocoding fails (network error, address not found), the location simply has no coordinates until a later sync's address-changed check happens to re-attempt it — which it won't, since the address hasn't changed. Accepted trade-off, see Risks.
- **A `CustomerLocationChangeType` enum and `CustomerLocationSyncLog` table mirror `CustomerChangeType`/`CustomerSyncLog` exactly** (same four change types — created/updated/deleted/restored — same columns: location id, change type, `occurred_at` server-default). `sync_customer_locations` writes one log row per reconciliation outcome, the same points in the loop where `sync_customers` already does. Kept as its own table rather than a shared/polymorphic log — matches the existing precedent of one log table per synced entity, and avoids a nullable-FK-per-entity-type design that neither table currently needs.

## Risks / Trade-offs

- [A customer location synced outside of seeding (e.g. a new delivery address linked in Tripletex after initial setup) has no region at all, and is therefore permanently unschedulable by the optimizer until the future geofencing feature ships or a human mechanism to set it exists] → Accepted; this is the explicit trade-off of deferring region assignment rather than inventing a throwaway derivation now. The location is still fully visible and manually assignable everywhere except the optimizer.
- [This Tripletex account's real addresses are Norwegian; the app's existing demo employees and their region scoping are Dutch (Amsterdam, Utrecht, Rotterdam)] → Accepted for now: even where seed data assigns a region to make the demo work, it's picking from the existing Dutch region set, not a real Norwegian one — the demo's regions and its real address data are cosmetically mismatched until both employee fixtures and real region masterdata converge, a separate, later concern.
- [A location whose geocoding fails (bad address, geocoder down) never gets coordinates because nothing re-triggers geocoding for an unchanged address] → Mitigation: touching the address in Tripletex (even a no-op re-save) changes the fields and triggers a re-attempt on the next sync; a manual retry-all option could be added later if this proves to be a real problem in practice.
- [The public Nominatim instance's 1-request/second policy makes a large initial sync slow] → Accepted; the number of locations in play here is small (a handful of demo delivery addresses), and the rate limit only applies to genuinely new/changed addresses, not every sync.
- [Truncating `customer_locations` cascades into `contracts`/`service_visits`/`assignments`, destroying whatever demo scheduling data exists at migration time] → Same accepted trade-off as the original customer-id migration; seed data is rebuilt fresh afterward per the Migration Plan below.

## Migration Plan

1. Add the geocoding dependency (`geopy`) to `backend/requirements.txt`.
2. Extend `CustomerLocation` with Tripletex-sourced structured address fields (mirroring `Customer`'s pattern), a `delete_flag`, and make `latitude`/`longitude` and `region_id` nullable; add `CustomerLocationChangeType` and `CustomerLocationSyncLog` (mirroring `CustomerChangeType`/`CustomerSyncLog`); migration truncates `customer_locations`/`contracts`/`service_visits`/`assignments`, switches `id` to non-autoincrement, and creates the new log table, matching `0004_tripletex_customers.py`'s shape.
3. Add a geocoding module wrapping `geopy` + Nominatim with the required rate limiter and user agent.
4. Add `sync_customer_locations` to `backend/app/tripletex.py`: fetch `/deliveryAddress`, filter to records with a locally-known linked customer, reconcile create/update/soft-delete/restore (never touching `region_id`), geocoding only changed/new addresses, and writing a `CustomerLocationSyncLog` entry for each create/update/delete/restore.
5. Call `sync_customer_locations` right after `sync_customers` in the backend's startup lifespan and inside the existing `POST /customers/sync` endpoint.
6. Update `build_optimize_payload` to exclude a candidate visit whose location has no resolved coordinates or no assigned region.
7. Rework `backend/app/seed.py` to sync customer locations (instead of hand-creating them), assign each one a region itself (current seed mapping, then random for extras), and build its demo contracts against whatever locations come back, dropping any fixture that no longer has a location to attach to (same "map what's available, drop the rest" approach already used for customers).
8. Verify: a Tripletex delivery address linked to a known customer produces a local customer location with resolved coordinates and no region; removing that link (or the address) soft-deletes it locally; re-adding it restores it without touching its region; a location without resolved coordinates or without a region is excluded from a schedule run but still viewable and manually assignable; seed data ends up with every demo location assigned a region; the Customer Portal's existing Refresh action shows updated locations correctly. (Region/coordinates becoming nullable did require frontend null-safety fixes, contrary to the original assumption — see proposal.md - Impact.)
9. Rollback: revert the migration (drop the new columns, restore autoincrement and `region_id` non-null) and the sync/seed changes; same blast radius as the original customer sync's rollback.
