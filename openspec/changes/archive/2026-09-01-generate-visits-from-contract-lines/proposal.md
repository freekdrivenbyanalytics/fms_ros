## Why

Creating a contract line in the Customer Portal today persists the line itself but generates no service visits at all — the only way visits ever exist is via the one-time seed script. Planners need visits to appear automatically so newly-contracted work actually shows up for assignment, and they need the Manual Assignment board to stay usable once visits are generated automatically at scale, rather than dumping every visit ever created into one unbounded list.

## What Changes

- **BREAKING**: When a contract line is created, the system now generates one unassigned service visit per occurrence (start_date, then every `interval_days` after that) up to the contract line's `end_date` if set, or up to 365 days (one year) after `start_date` if it has no end date. This replaces the current explicit behavior ("no service visits generated as a result").
- Updating an existing contract line does **not** regenerate, modify, or delete any service visits — visit generation happens once, at creation, only. (An open-ended line's occurrences beyond the one-year horizon are not generated by this change; extending that horizon further into the future is out of scope here.)
- The Customer Portal's Contracts view shows, for each contract line, the service visits generated from it (requested date and status).
- The Manual Assignment board (`assign` view) gains a date-range control shared by both the unassigned and assigned visit lists: by default it shows every visit requested before today (no lower bound — an overdue unassigned visit is never hidden by the range) through 7 days from today, with "This Week" and "4 Weeks" presets that move the range's upper bound out further (end of the current calendar week, or 28 days out) without ever excluding overdue visits.
- `GET /service-visits` gains optional `start_date`/`end_date` query parameters to support the above; omitting them preserves today's unfiltered behavior for any other caller.

## Capabilities

### Modified Capabilities
- `contracts`: creating a contract line now generates service visits (was explicitly "no service visits generated"); updating one explicitly does not.
- `service-visits`: adds the generation rule (occurrence dates, one-year horizon for open-ended lines) and optional date-range filtering on the list endpoint.
- `customer-portal`: contract lines in the Contracts view show their generated service visits.
- `assignments`: the Manual Assignment page's employee/visit lists gain a shared date-range control with the default range and presets described above.

## Impact

- Backend: `create_contract_line` (backend/app/main.py) generates `ServiceVisit` rows after persisting the line; `GET /service-visits` accepts optional `start_date`/`end_date` query params; a new occurrence-date helper shared by the endpoint (and reusable by seed data going forward, though updating `seed.py` itself is out of scope for this change).
- Frontend: `frontend/src/customer-portal/ContractsView.tsx`'s `ContractLineRow` shows the line's generated visits; `frontend/src/App.tsx`'s `assign` view gains a date-range control (default + "This Week"/"4 Weeks" presets) that scopes both `UnassignedVisitList` and `AssignedVisitList`; `listServiceVisits` in `frontend/src/api.ts` accepts optional date params.
- No change to the route optimizer's own visit selection logic (`solver_client.py` queries `ServiceVisit` directly, not through this endpoint, and is unaffected by the new query parameters or the Manual Assignment board's display filter).
