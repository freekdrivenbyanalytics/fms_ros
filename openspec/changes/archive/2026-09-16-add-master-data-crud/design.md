## Context

`Customer`, `CustomerLocation`, and `Product` (`backend/app/models.py`) are today entirely Tripletex-sourced: their primary key is Tripletex's own id, and `sync_customers`/`sync_customer_locations`/`sync_products` (`backend/app/tripletex.py`) are the only thing that ever creates or updates one. None has a create/update/delete endpoint. `TripletexClient` (`backend/app/tripletex.py`) already has `create_customer`/`update_customer`/`delete_customer` (the latter two added for the Resco integration work); it has no product methods at all, and no standalone delivery-address create.

This design follows the same shape already established for Resco pushes (`backend/app/resco.py`): a client method per entity/operation, a `resco_*_id` column remembering the created record for upsert. The new piece here is the *Tripletex* side of the same idea — creating a record in fms_ros first and adopting Tripletex's returned id, rather than only ever pulling Tripletex's existing records in.

**Delivery-address creation mechanism — resolved:** verified live against a throwaway customer. `PUT /customer/{id}` with a nested `{"deliveryAddress": {...}}` object creates a genuinely new, independent delivery address every time it's called — confirmed by calling it twice on the same customer and seeing two distinct delivery-address ids, both real and independently retrievable via `get_delivery_addresses()`, afterward. This is the same mechanism the `physicalAddress`-side-effect incident stumbled into accidentally (see `openspec/changes/archive/2026-09-16-sync-customers-to-resco/design.md`), except here it's the *intended* way to add a location, not an accidental one — `deliveryAddress` is the correct key to nest for this purpose; `physicalAddress` is the customer's own separate address and must never be used for locations (per that incident). Updating an *existing* delivery address still goes through the already-proven `PUT /deliveryAddress/{id}` directly (confirmed live during that same incident's cleanup) — the customer-level nested-object call is only for creating a new one, never for editing one in place.

## Goals / Non-Goals

**Goals:**
- Customer, customer location, and product each get a create/update/soft-delete path in fms_ros that pushes to Tripletex (and, for customers and products, Resco — customer locations already push to Resco as Assets from the prior change).
- Existing Tripletex-sourced data needs no migration or re-seeding: every current row already carries Tripletex's real id as its primary key, so the only change is *where new rows can originate*.

**Non-Goals:**
- Any change to what triggers Tripletex/Resco *sync* (pulling changes in) — `sync_customers`/`sync_customer_locations`/`sync_products` and their automatic Resco pushes are unchanged; this change only adds the reverse (push-out) direction for locally-initiated creates/updates.
- Hard delete, anywhere — soft-delete only, matching every other entity in this codebase, and matching the hard constraint that Tripletex has no delete operation for a delivery address at all.
- Any UI/behavior change to the Customer Portal (customer-facing) — this is Admin Portal (staff) only, matching where Product/Customer Location management already lives.
- Skills, service-order-types, or anything about employee qualification — that is a separate change (`add-skills-and-service-order-types`).

## Decisions

**Creating a customer never creates a customer location in the same call.** Since the only confirmed way to attach a delivery address to a customer is nested inside a customer *create* payload, always doing so would makes a new customer's *first* location a special case (bundled into customer creation) while every subsequent location goes through a different, separately-verified mechanism. Simpler and more consistent: customer creation only ever sends `name` (Tripletex's realistic minimum), and every customer location — including a brand-new customer's first — is always created through the same, single customer-location-create path. This also sidesteps ever sending a customer-level address at all, avoiding the entire class of side effect the prior change hit.

**Product creation's required fields — resolved:** verified live. `POST /product` with only `number`/`name` succeeds (`201`); Tripletex fills in every other field (VAT type, currency, etc.) with sensible defaults. Also discovered live: `DELETE /product/{id}` actually works (`204`, confirmed gone from a subsequent list) — unlike customer/delivery-address deletion, Tripletex does support removing a product. This change's soft-delete still never calls it (see the soft-delete decision below — the "never destroy upstream data" principle applies regardless of whether Tripletex *could* support a real delete), but it's worth knowing this endpoint exists for `create_product`'s own throwaway-verification hygiene, and for anyone revisiting this decision later.

**Soft-delete never calls Tripletex at all — and needs a field distinct from the existing `delete_flag`, to avoid a real conflict with the sync's own restore logic.** Deleting a customer or product locally doesn't delete it in Tripletex (mirrors the employee/Resco precedent of "push what we can, never destroy upstream data"), and customer locations *can't* be deleted in Tripletex regardless (confirmed live in the prior change: `DELETE /deliveryAddress/{id}` returns `405`).

The existing `delete_flag` on all three entities is sync-managed: `sync_customers`/`sync_customer_locations`/`sync_products` set it when a record disappears from Tripletex's returned list, and *clear it again* ("restore") if that same record reappears — by design, so a customer accidentally deleted then undeleted in Tripletex reflects correctly in fms_ros. If the new local soft-delete reused `delete_flag`, the very next Tripletex sync would immediately clear it right back, since the record was never actually removed from Tripletex — sync would see it "reappear" (it never left) and restore it, undoing the user's delete. So this change adds a second, independent flag — `archived` — set only by the new soft-delete endpoints, never touched by any sync function, and combined with `delete_flag` in every list query's default filter (`WHERE NOT delete_flag AND NOT archived`). The two flags answer different questions: `delete_flag` = "does Tripletex still have this," `archived` = "did staff hide this in fms_ros regardless." An archived record whose Tripletex counterpart later gets legitimately deleted still ends up with both flags set, which is fine — either one already excludes it from every list.

**Update pushes happen synchronously, best-effort, in the same request as the local update** — matching the existing employee-update-triggers-Resco-sync pattern, not a queued/background job. A Tripletex push failure on update does not fail the local update (mirrors the existing "automatic Resco sync never blocks the triggering action" principle already established for employees/customers/locations), but a push failure on *create* does fail the create — an entity that fms_ros treats as "the master" needs to actually exist upstream from the moment it's created, unlike an update to an already-existing, already-linked record where a transient push failure just means the next sync reconciles it.

**Product type field, added during implementation to close a real gap found while building product creation.** `sync_products`'s pull from Tripletex (`TripletexClient.get_products`) only returns products whose `number` starts with `PRODUCT_NUMBER_PREFIX` ("TJN") — anything else is invisible to the sync entirely. Since `sync_products` treats a known local product id that's absent from that pull as deleted (sets `delete_flag`), a product created locally through this change's new endpoint with a number that *doesn't* start with "TJN" would get incorrectly marked deleted on the very next sync. Resolved (per explicit user direction) by adding a `product_type` field (`TJN` = tjeneste/service, `PRD` = produkt/product) to `Product`: `ProductCreate`/`ProductUpdate` take a `product_type` alongside `number`, and the create/update endpoints prefix the given number with the product type (skipping the prefix if the number already starts with it) before sending it to Tripletex and storing it locally. `TripletexClient.get_products`'s filter is widened from a single `PRODUCT_NUMBER_PREFIX` to a `PRODUCT_NUMBER_PREFIXES` tuple (`"TJN"`, `"PRD"`), so both product types stay in the sync's scope. `product_type` itself is never trusted as an independently-set value — `_apply_product_fields` (used by both the regular Tripletex sync and, indirectly, by anything that re-derives product state) always recomputes it from the actual `number` prefix, so it can never drift out of sync with the one field Tripletex actually owns. Existing products all already use the "TJN" prefix, so the migration backfills `product_type` via a column default of `"TJN"` — accurate for every current row, no per-row inspection needed.

**Resco push for the three entities reuses the exact shape already built**: customers already push to Resco as Accounts and customer locations as Assets (`sync_customer`/`sync_customer_location` in `backend/app/resco.py`, from the prior change) — creating/updating one through this change's new endpoints calls the same functions afterward, no new Resco code needed for those two. Only Product is new: `RescoClient.create_product`/`update_product` sending `name`/`productnumber` to Resco's `product` entity set (confirmed live to exist, via `$metadata`), plus a `resco_product_id` column on `Product` and `sync_product`/`sync_products_to_resco` functions mirroring the existing ones.

## Risks / Trade-offs

**Reusing the existing `delete_flag` for local soft-delete would have silently broken on the very next Tripletex sync** (see the `archived` decision above) — caught during design rather than discovered as a "delete doesn't stick" bug after implementation. No remaining risk once `archived` is a field the sync functions never touch.

**Making these three entities creatable/editable in fms_ros is a real shift in where masterdata truth lives**, and a mistake here (e.g. a bad push) now touches a live, shared Tripletex/Resco org, not just local data. → Mitigation: every new push method is verified live with a throwaway record (create, confirm, delete/revert) before being relied on for real data, following the same discipline used throughout this codebase's Tripletex/Resco integration work.

## Migration Plan

Additive: `resco_product_id` on `Product` (nullable). No backfill — existing products simply start unsynced to Resco, same as customers/locations did before their own Resco change. No data migration needed for the Tripletex-sourced-vs-locally-created distinction, since there isn't one at the data level — every row's primary key is already Tripletex's real id regardless of where it originated.
