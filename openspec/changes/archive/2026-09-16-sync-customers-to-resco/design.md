## Context

`Customer` and `CustomerLocation` (`backend/app/models.py`) are wholly Tripletex-sourced today except `CustomerLocation.region_id`/`latitude`/`longitude`/`coordinates_locked` (local-only fields, protected from sync overwrite by `coordinates_locked` — see `_apply_location_fields` in `backend/app/tripletex.py`). `TripletexClient` currently has `create_customer`/`delete_customer` but no `update_customer` — nothing has ever needed to push a change back to Tripletex before.

This design follows directly from the employee → Resco integration (`backend/app/resco.py`, archived under `openspec/changes/archive/2026-09-14-sync-employees-to-resco/`), reusing its shape: a `RescoClient` method per entity/operation, a `resco_*_id` column remembering the created record for upsert, and a `RescoSyncSummary`/per-entity result type. Unlike that integration, this one starts with the real, live-verified Resco schema (fetched via `$metadata` and sample reads against `https://sfm.rescocrm.com/odata/v4/sfm/`) rather than a guess, so most of the API-shape risk from that first integration doesn't repeat here.

**Real data finding that drives this design:** querying live Tripletex data shows all 150 current customers have `email`, `phoneNumber`, and `organizationNumber` as empty strings. Since Tripletex customer records can be updated via its API, the fix is a one-time seed of realistic values into Tripletex itself (see Decisions), rather than a local fms_ros override — keeping Tripletex as the sole source of truth.

**Incident during implementation, and why the design changed mid-flight:** the first version of the one-time seed script also set each customer's `physicalAddress` (so the Resco Account would have an address). Testing revealed a real Tripletex API side effect: `PUT /customer/{id}` with a `physicalAddress` object doesn't just update that field — it creates a brand-new delivery address (what fms_ros calls a "customer location") as a side effect, on top of whatever real location(s) the customer already had. Because the seed script ran against all 150 real customers before this was caught, it produced 150 stray duplicate locations (plus 3 more from earlier manual verification on one customer), all synced into fms_ros and then into Resco as real duplicate Assets before the problem was noticed.

This was cleaned up as follows, and the design changed to avoid the root cause entirely:
- Deleted the resulting duplicate Assets from Resco and blanked (Tripletex has no delete endpoint for delivery addresses — confirmed live, `DELETE` returns `405`) the 153 stray delivery addresses' address fields, so they read as empty rather than showing fabricated addresses.
- The corrected design **no longer sets a customer-level `physicalAddress` at all.** The one-time seed script now only sends `email`/`phoneNumber`/`organizationNumber` (verified live that these alone do **not** trigger the stray-location side effect). The Resco Account's address fields are instead sourced from the customer's own, already-real, already-correctly-located `CustomerLocation` — sidestepping the problem entirely and requiring no Tripletex writes for address data at all.
- `Customer` gained (via migration 0016) then dropped again (via migration 0017) `resco_address_line1`/`resco_city`/`resco_postal_code`/`resco_country` — briefly part of the design before this incident forced the pivot away from customer-level addresses.

**Confirmed live Resco schema** (org `sfm`, `https://sfm.rescocrm.com/odata/v4/sfm/`):
- Account: entity set `account`, fields `name`, `emailaddress1`, `telephone1`, `vatid`, `address1_line1`, `address1_city`, `address1_postalcode`, `address1_country`. `id` is a server-generated GUID string, same as `systemuser`. No annotation marks `name` as computed (unlike `systemuser.name`), so it's directly settable.
- Asset: entity set `fs_asset`, fields `name`, `serialnumber`, `installation`, `serviceinterval`/`serviceintervalevery`, `price`, plus lookups `__customerid_id` (a polymorphic Dynamics-style "customer" reference to an Account or Contact), `__fs_product_id`, `__resco_functionallocationid_id`. No address fields at all — an Asset's location is implicit through its linked Account/Contact.

## Goals / Non-Goals

**Goals:**
- Push every customer to Resco as an Account and every customer location to Resco as an Asset, upserting via a remembered Resco ID, mirroring the employee integration's shape.
- Seed this sandbox's existing Tripletex customers with realistic email/phone/org-number data, once, so the normal Tripletex→fms_ros→Resco pipeline has real data to carry through — no parallel local editing surface, and no customer-level address writes (see Context).
- Keep Tripletex as the sole source of truth for customer contact data, exactly as it already is for every other customer field.

**Non-Goals:**
- Pulling Account/Asset data back from Resco (push-only, same as employees).
- Syncing any other Resco entity (Contact, Functional Location, Product) — an Asset's optional `__fs_product_id`/`__resco_functionallocationid_id` links are left unset.
- Any locally-editable override/lock mechanism for customer contact fields — fixing the data at its Tripletex source (a one-time seed) covers this instead.
- Writing a customer-level `physicalAddress` to Tripletex, ever — see the incident in Context. The Resco Account's address always comes from an existing `CustomerLocation`.
- A permanent, reusable "seed contacts" tool — the CSV-based Tripletex seeding is a one-off implementation task for this sandbox's current ~150 customers, not part of `seed.py` or any ongoing tooling. A customer added to Tripletex later without full contact info simply stays incomplete in Resco too, same as it would in Tripletex's own UI today.
- Editing anything on `CustomerLocation` beyond remembering its `resco_asset_id` — an Asset only needs a name (the location's already-populated `address`) and its Account link, both already available without new local or Tripletex input.

## Decisions

**Seed only `email`/`phoneNumber`/`organizationNumber` into Tripletex via a one-time CSV + script — never `physicalAddress`.** A CSV (realistic fake values for this sandbox's ~150 existing demo customers, matched by Tripletex customer id) is read by a small script calling a new `TripletexClient.update_customer` method per row. One-off implementation task, run once against the live Tripletex sandbox; not wired into `seed.py`, backend startup, or any repeatable pipeline. `physicalAddress` is deliberately excluded per the incident in Context.

**The Resco Account's address fields are sourced from the customer's own `CustomerLocation` — specifically its first non-deleted location that actually has a street address, not just its first non-deleted location.** `RescoClient._account_payload` reads `address1_line1`/`address1_city`/`address1_postalcode` from that location's `address_line_1`/`city`/`postal_code`, and `address1_country` from its `country` JSONB's `name`. The "has a street address" filter matters in practice: every customer currently has at least one blanked stray location left over from the incident above (`address_line_1` empty), so picking merely "first non-deleted" would non-deterministically source the Account's address from an empty record roughly as often as from the real one, depending on unordered relationship iteration. This reuses real, already-correct address data (the same data driving the routing/scheduling demo) instead of introducing a second, separate address concept on `Customer` — and requires zero Tripletex writes for address data.

**Both Resco syncs run automatically right after their Tripletex counterpart, not on individual entity mutation (there is none to hook), plus a manual button.** Concretely: `sync_customers()` calls a new `sync_customers_to_resco(db)` at the end (best-effort, exceptions logged not raised); `sync_customer_locations()` does the same with `sync_customer_locations_to_resco(db)` — preserving the existing customer-before-locations ordering, which also happens to be exactly the ordering Resco needs (an Asset's Account must exist first). New endpoints `POST /customers/sync-resco` and `POST /customer-locations/sync-resco` expose the same functions for manual triggering, following `POST /employees/sync-resco`'s shape.

**A customer location whose customer has no `resco_account_id` yet is skipped and reported, not failed or blocked.** Matches the employee integration's "skip, don't fail" shape for missing prerequisites. Since customer sync always runs immediately before location sync (same order as the Tripletex sync it follows), this mainly matters for a location whose customer's own Resco sync failed (e.g. Resco temporarily unreachable) — it self-heals on the next sync pass once the customer succeeds.

**A customer location with no street address (`address_line_1` blank) is also skipped, not synced.** Added specifically to stop the 153 blanked stray locations from the incident above from ever being re-synced to Resco as (now-empty) Assets again — Tripletex still returns them (it has no delete endpoint), so without this guard every future sync would recreate the Assets just deleted during cleanup.

**The Admin Portal gains a new, read-only "Customers" view (list + detail), placed there rather than in Customer Portal.** Customer Portal already shows customers, but doubles as a customer-facing self-service simulation via its "viewing as" selector — putting Resco sync-status there risks a real customer eventually seeing internal integration plumbing through that simulation. Admin Portal is already staff-only and already holds the equivalent Customer Locations view, so the new Customers view sits next to it. No edit form is needed here since there's no local field left to edit.

## Risks / Trade-offs

~~The exact write syntax for an Asset's Account link is unconfirmed.~~ **Resolved:** verified live with a throwaway Account + Asset (created, confirmed linked via a fresh read, then both deleted). The correct syntax is a Dynamics-style `@odata.bind` annotation named `<lookup>_<targetentity>@odata.bind`: `{"customerid_account@odata.bind": "/account({account_id})"}` (no braces/quotes around the GUID). The resulting Asset's `__customerid_id` read back exactly matches the Account's id.

~~The exact Tripletex API shape for updating a customer's contact fields is unconfirmed, including whether `organizationNumber` can even be changed post-creation via the API.~~ **Resolved:** verified live via `PUT /customer/{id}` on a real customer (updated then reverted to its original blank state). `email`, `phoneNumber`, and `organizationNumber` are all freely editable post-creation — no restriction encountered.

**Materialized risk: `PUT /customer/{id}` with a `physicalAddress` object silently creates a new delivery address (customer location) as a side effect, rather than updating in place.** This was not caught until after the one-time seed script had already run against all 150 real customers, producing 153 stray duplicate locations that also got synced into Resco as real Assets before detection. → Mitigation applied: the design was changed to never write `physicalAddress` to Tripletex at all (Resco Account addresses are sourced from an existing `CustomerLocation` instead — see Decisions); the stray locations' Resco Assets were deleted and their Tripletex address fields blanked; a "skip if no street address" guard in `sync_customer_location` stops the now-blank stray locations from being re-synced to Resco in the future, since Tripletex has no way to truly delete them (`DELETE /deliveryAddress/{id}` returns `405`, confirmed live) and will keep returning them on every future sync.

**Materialized (unrelated, tooling) finding while cleaning up the above: bulk `DELETE /fs_asset('{id})` calls consistently failed with `401 AccessDenied` — not a real auth or rate-limit issue.** The same credentials and asset ids succeeded reliably every time when run as a short foreground command, and failed 100% of the time when run via a backgrounded/long-running process (explicit or auto-backgrounded after exceeding a shell timeout) — regardless of request pacing. Not relevant to the shipped code (no runtime code deletes Resco records), but worth knowing for anyone doing bulk cleanup against this Resco org by hand: run `DELETE` calls in short foreground batches, not a single long-running background script.

**Running the Resco push automatically after every Tripletex sync means every backend restart (frequent under `uvicorn --reload` in dev) re-syncs all customers/locations to Resco, unlike the employee integration where automatic sync only fires on an explicit create/update action.** → Accepted (same trade-off already accepted for the employee integration's own automatic trigger); mitigated in practice by the upsert-by-remembered-ID shape (an unchanged customer becomes a no-op-ish `PATCH` with the same values, not a duplicate).

## Migration Plan

Additive: new nullable columns on `Customer` (`resco_account_id`) and `CustomerLocation` (`resco_asset_id`). `resco_address_line1`/`resco_city`/`resco_postal_code`/`resco_country` were added on `Customer` in migration 0016 then dropped again in migration 0017 once the design moved to sourcing the Account's address from `CustomerLocation` instead (see Context). No backfill needed for any of it — every existing customer/location simply starts with these fields empty, and the one-time Tripletex seed + next sync populate what they can. No rollback complexity beyond standard down-migrations dropping the columns.
