## Context

`backend/app/models.py`'s `Customer` currently has only `id` (autoincrement PK) and `name`, created purely by `backend/app/seed.py` (see `backend/alembic/versions/0002_customer_regions.py`). `backend/app/config.py` uses `pydantic-settings` with `env_file=".env"` (resolved relative to the backend working directory, per README's `cd backend` setup step); `backend/.gitignore` already ignores `.env`. `backend/requirements.txt` has no HTTP client library yet. `backend/app/main.py` has no startup hook today. `customer_locations.customer_id` is the only foreign key referencing `customers.id`; `contracts` references `customer_locations`, not `customers`, directly. See proposal.md - Why / What Changes for motivation and scope; see specs/customers/spec.md and specs/customer-portal/spec.md (deltas) for required behavior.

## Goals / Non-Goals

**Goals:**
- Make Tripletex the source of truth for customer data, with `customers.id` being Tripletex's own customer id (no separate app-only id), so every table that already references a customer keeps working unchanged.
- Keep all Tripletex credentials and traffic server-side; the frontend only ever calls this app's own backend.
- Let `backend/app/seed.py` keep producing the same demo scenario (locations/contracts/visits) it does today, just attached to real Tripletex-sourced customers instead of fictional ones.
- Keep the backend startable even when Tripletex is unreachable (a POC dev machine may not always have a valid `.local/api_key` or network access).

**Non-Goals:**
- No UI for editing customer data — the portal remains read-only except for the new Refresh action, which re-syncs from Tripletex, not from user edits.
- No multi-worker-safe session-token cache — an in-memory cache scoped to a single backend process is sufficient for this POC's single-process dev setup.
- No consumer-token/employee-token Tripletex auth flow — explicitly deferred per the confirmed auth decision; `TripletexClient` is structured so that flow can be added later without changing its public interface.
- No general Tripletex integration beyond customers (no orders, invoices, products, etc.).

## Decisions

- **`customers.id` becomes a plain (non-autoincrement) Integer primary key populated from Tripletex's customer id**, not an app-generated identity. Alternative considered: keep an app-only autoincrement PK and add a separate unique `tripletex_id` column — rejected per the confirmed decision to define the customers table using only Tripletex's own fields, and because it would require every consumer to translate between the two ids for no benefit in this single-source-of-truth setup.
- **Exact Tripletex field list is discovered, not assumed.** Tripletex's `/customer` resource is known to be fairly rich (contact info, addresses, invoicing settings, etc.) but the precise shape can't be confirmed without a live call. Task 1 in tasks.md is a discovery step: call Tripletex's customer endpoint once and record the actual response shape. The migration (task 2) maps that response onto columns: flat scalar fields (strings, numbers, booleans — e.g. name, email, organization number) become their own typed columns; nested or list-valued fields (e.g. postal/physical address objects, bank account lists) are stored as `JSONB` columns, so "all fields from there" is captured faithfully without inventing a deep relational schema for structures this app doesn't otherwise use. This keeps the spec-level behavior ("fields sourced from Tripletex") stable regardless of exactly which columns result.
- **`TripletexClient` implements the confirmed auth flow behind a small interface**: reads the refresh token from `backend/.local/api_key` (a single line, not `.env` — kept separate per the request, since it's a long-lived secret distinct from ordinary config), exchanges it for a session token via `POST {TRIPLETEX_BASE_URL}/token/session/:createFromRefreshToken` with `refreshToken` and `ttlSeconds`, caches the session token and its expiry in memory, and re-exchanges shortly before expiry. Subsequent Tripletex calls use HTTP Basic auth with username `"0"` and the session token as password. `TRIPLETEX_BASE_URL` and `TRIPLETEX_SESSION_TTL_SECONDS` are added to `Settings` (`backend/app/config.py`, sourced from `.env` like `database_url` already is), so test/demo vs. production Tripletex environments are switchable without code changes. `httpx` is added to `backend/requirements.txt` as the HTTP client.
- **A single reusable `sync_customers(db)` function** (e.g. `backend/app/tripletex.py`) performs the fetch-and-reconcile (add/update/soft-delete/revive) described in specs/customers/spec.md, used by all three triggers: a FastAPI startup hook, a new `POST /customers/sync` endpoint, and `backend/app/seed.py`.
- **Soft delete via a `delete_flag` boolean column** (default `false`) on `Customer`, not a hard delete. A customer absent from the Tripletex response has `delete_flag` set to `true`; a previously-flagged customer present again has it cleared and its fields refreshed. No FK `ondelete` behavior is needed — the customer row, and everything referencing it, is never removed by a sync. `list_customers` (`GET /customers`) filters `WHERE delete_flag IS FALSE` so flagged customers are hidden by default, per specs/customers/spec.md's "Deleted customers are hidden by default". Alternative considered: hard delete with `ondelete="CASCADE"` (the original design) — rejected per the confirmed decision, since it destroys local operational history (locations/contracts/visits/assignments) the moment Tripletex drops a customer, which is unnecessarily destructive for what may be a transient or mistaken removal upstream.
- **Startup hook is resilient**: added via FastAPI's lifespan, it calls `sync_customers` inside a try/except and logs a warning on failure (missing `.local/api_key`, Tripletex unreachable, etc.) rather than raising, so `uvicorn app.main:app` still starts. The on-demand endpoint and the seed script, by contrast, let a sync failure surface as an error (a 502 for the endpoint, an exception that stops seeding) since both are explicit, user-initiated actions where silent failure would be worse than a clear one.
- **`backend/app/seed.py` calls `sync_customers(db)` first**, then queries the resulting customers ordered by `id` ascending, and attaches the existing fixture `CustomerLocation`/`Contract`/`ServiceVisit` data (unchanged in shape) to the first four, positionally, in the same order as today's `van_der_berg, bakker, de_jong, visser` fixtures. Any Tripletex customers beyond the first four are left with no locations/contracts, which is a realistic and acceptable state (a real customer may genuinely have none yet).
- **`customer_sync_log` is a lean event log, not a diff/snapshot store**: `id` (normal autoincrement — unlike `customers.id`, this is an app-internal id, not Tripletex-sourced), `customer_id` (FK to `customers.id`), `change_type` (enum: `created`/`updated`/`deleted`/`restored`), `occurred_at` (timestamp, defaults to now). `sync_customers(db)` writes one row per customer it creates, updates, delete-flags, or restores, in the same transaction as the change itself. No field-level before/after values are captured, and no API or UI exposes this log yet — both are deferred, since only an audit trail of *what happened and when* was requested. Alternative considered: also storing a JSONB snapshot of the customer's fields per entry — rejected for now as unrequested scope; can be added later without breaking this shape if richer auditing is needed.
- **Frontend**: `frontend/src/api.ts` gets a `syncCustomers()` POST call; `CustomersView.tsx` gets a "Refresh" button (in the unscoped list view) that calls it, then re-fetches customers, customer locations, and contracts (via callbacks passed from `CustomerPortalApp.tsx`, mirroring how data is already fetched there) — needed because a sync can delete customers and cascade to locations/contracts, so those two lists can also change. `Customer` in `frontend/src/types.ts` and `CustomerOut` in `backend/app/schemas.py` gain whatever fields the migration adds; the Customers list/detail views show them (exact fields finalized alongside the migration).

## Risks / Trade-offs

- [Delete-flagged customers accumulate indefinitely — nothing ever purges them] → Accepted for this POC; a future change can add retention/purge logic or an admin view of deleted customers if needed.
- [A real Tripletex customer id could collide with a delete-flagged row left over from a differently-sourced customer, if this app ever gains a second data source] → Not a concern today (Tripletex is the only source), but worth remembering if that changes.
- [Startup sync adds a network round-trip to backend boot, and a slow/unreachable Tripletex could noticeably delay startup before the resilience try/except kicks in] → Mitigation: keep the HTTP client's connect/read timeouts short (a few seconds) so an unreachable Tripletex fails fast rather than hanging startup.
- [The exact Tripletex field list is unknown until implementation] → Mitigation: task 1 is a dedicated discovery step before any schema work begins, so the migration is written against real data, not guesses.
- [`op.create_table`'s default `Integer, primary_key=True, autoincrement=True` created `customers.id` as a Postgres SERIAL-backed column] → The migration must explicitly drop that default/sequence (`ALTER TABLE customers ALTER COLUMN id DROP DEFAULT`, dropping the now-unused sequence) so app-supplied Tripletex ids can be inserted directly.

## Migration Plan

1. Discovery (task 1): call Tripletex's customer endpoint with real credentials and record the response shape.
2. Add an Alembic migration that: truncates `customer_locations`, `contracts`, `service_visits`, and `assignments` (their existing rows reference the fictional customers about to be removed, and will be re-created by the restructured seed — this one-time cleanup also avoids a leftover fictional customer id colliding with a real Tripletex id later), drops the `customers.id` SERIAL default/sequence, and replaces the now-obsolete `name`-only shape with the discovered field set plus a `delete_flag` boolean column (default `false`). This is intentionally destructive to existing local demo data — acceptable since `backend/app/seed.py` recreates it from Tripletex afterward, but a developer with an existing local database should expect to re-run `python -m app.seed` after migrating.
3. Update `backend/app/models.py`, `backend/app/schemas.py`, `frontend/src/types.ts` to match the discovered fields.
4. Implement `TripletexClient` and `sync_customers`, wire the startup hook and `POST /customers/sync` endpoint, update `backend/app/seed.py`.
5. Update the frontend Customer Portal (Refresh button, new fields).
6. Rollback: `alembic downgrade` restores the previous `{id (autoincrement), name}` shape; a developer would need to re-seed with the old (pre-Tripletex) seed logic from version control if reverting this change entirely.
