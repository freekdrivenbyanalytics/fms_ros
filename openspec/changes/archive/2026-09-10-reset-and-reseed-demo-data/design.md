## Context

`TripletexClient` (`backend/app/tripletex.py`) currently only supports GET (`get_customers`, `get_delivery_addresses`, `get_products`), authenticated via a refresh-token → session-token exchange (`self._auth()` returns `httpx.BasicAuth("0", session_token)`). There is no create or delete method for anything, and no local hard-delete path for customers/customer locations — `sync_customers`/`sync_customer_locations` only ever soft-delete (`delete_flag = True`) a local record that disappears from Tripletex.

Verified against Tripletex's live OpenAPI spec (`https://tripletex.no/v2/openapi.json`) and by direct API calls during implementation: `/deliveryAddress` (collection) supports only GET, and `/deliveryAddress/{id}` supports only GET/PUT — there is no create or delete endpoint for a delivery address as a standalone resource. A customer's delivery address is created only as a side effect of `POST /customer` when the payload includes a `deliveryAddress` object; the response's `deliveryAddress.id` is that address's Tripletex id (and becomes the local `CustomerLocation.id` once synced). Deleting the owning customer (`DELETE /customer/{id}`, which the API does support) cascades away that delivery address — confirmed live: creating a probe customer with an embedded `deliveryAddress` then deleting the customer left both the customer and its delivery address returning 404. This superseded the original assumption (both a `create_delivery_address` and `delete_delivery_address` client method) — those endpoints do not exist.

Also discovered live: `DELETE /customer/{id}` can return a 500 (no message) for a customer with pre-existing ledger/invoice history — observed once against Tripletex's own built-in sample company, though a later retry against the same (by-then otherwise empty) account deleted it successfully, suggesting the failure may be transient (e.g. a lock or rate-limit edge case) rather than a hard, permanent block. Either way, the reset script treats any single customer's delete failure as tolerable (log and skip) rather than aborting the whole run — see Decisions.

Coordinates are not resolved by a Maps API call from this script at all: `geocode_address` (`backend/app/geocoding.py`, via `geopy`'s `Nominatim`, rate-limited to 1 req/sec) is already invoked automatically inside the customer-location create/update path whenever a location's address changes and its coordinates aren't locked (per the `customers` capability's "coordinates are geocoded from its address" requirement). So once a customer location is created in Tripletex and pulled in by the existing sync, its coordinates resolve on their own — the reset script only needs to provide real, geocodable street addresses in the CSV, not pre-resolved coordinates.

Visit generation is not a standalone function — `generate_occurrence_dates(start_date, interval_days, end_date)` (`backend/app/visit_generation.py`) is called inline wherever a contract line is created (`create_contract_line` in `main.py`). The reset script imports and calls it the same way rather than re-deriving visit dates.

`seed.py` is a useful reference for patterns (Tripletex sync calls, `_get_or_create`) but its own visit-generation loop is a simplified `range(2)` reimplementation, not `generate_occurrence_dates` — the new script does not reuse that part.

## Goals / Non-Goals

**Goals:**
- Reuse the existing sync (`sync_customers`, `sync_customer_locations`) and visit-generation (`generate_occurrence_dates`) functions unchanged, rather than duplicating their logic.
- Make the destructive path (Tripletex deletion) require an explicit flag, since it acts on a live external system.
- Produce a fully re-runnable script: running it again just wipes and rebuilds again, no idempotency guard needed (unlike `seed.py`, which is designed to be safe to import at every startup).

**Non-Goals:**
- Drawing/adjusting region geo-shapes for the new customer spread, or running the solver against the generated visits — both explicitly called out as manual follow-up in the proposal.
- General-purpose Tripletex write support exposed via the API or Admin Portal — the new create/delete client methods exist only for this script to call directly.
- Employee CSV or employee creation/deletion — per the resolved scope, existing employees are kept as-is; only their `employee_products` are updated.
- Any change to how customer-location coordinates are resolved — the existing Nominatim geocoding path is reused untouched.

## Decisions

- **New `TripletexClient` write methods, limited to what the API actually supports.** Add `create_customer(data)` and `delete_customer(id)`, each using `self._auth()` and `httpx.Client`, mirroring `get_customers`/`get_delivery_addresses`. There is no `create_delivery_address`/`delete_delivery_address` — the API has no such endpoints (see Context). Instead, `create_customer`'s payload embeds a `deliveryAddress` object, and the response's `deliveryAddress.id` is captured directly as that location's future `CustomerLocation.id` — no separate call or id-matching step needed. Deletion only ever calls `delete_customer`; its cascade removes the delivery address.
- **A customer that fails to delete is skipped, not fatal.** `delete_customer` failures (e.g. Tripletex's built-in sample company, which the API refuses to delete) are caught per-customer, logged with the customer id/name/error, and the loop continues. The "every customer is deleted" requirement becomes best-effort: everything deletable is deleted, and what isn't is reported rather than silently ignored or left to crash the whole run.
- **Explicit `--confirm` flag, refuse without it.** The script is invoked like `python -m app.reset_demo_data --confirm`; without the flag it exits immediately after printing what it would do, performing no Tripletex or database writes. This is the only safeguard requested — no dry-run diff, no environment allowlist — keeping it simple since the user has already accepted responsibility for pointing this at a safe Tripletex account.
- **Hard-delete order respects foreign keys**: assignments → service visits → `contract_line_products` join rows → contract lines → contracts → `CustomerLocationSyncLog` rows → customer locations → `CustomerSyncLog` rows → customers, mirroring the dependency order already implied by the schema's FK constraints (the same order `_delete_service_visits_for_line` and the contract-deletion cascade already narrow slices of). The sync-log tables were discovered live (a `ForeignKeyViolation` on the first hard-delete attempt) — they are not soft-delete bookkeeping that can be left behind, since their FK has no cascade.
- **Two bundled CSVs, generated once now as static demo content:**
  - `backend/app/demo_data/customers.csv`: one row per customer, with a shared `customer_key` column (a simple sequential key, e.g. `cust-001`) used only to line up each customer with its one location and contract line within this script run — never written back to Tripletex or persisted anywhere. Columns: `customer_key`, `name`, and address fields (street, postal code, city) real and geocodable — mostly Oslo, the rest Akershus (~75%/25%, a reasonable concentration matching "mostly Oslo" without the request pinning an exact ratio).
  - `backend/app/demo_data/contract_lines.csv`: one row per customer (this demo gives every customer exactly one location and one contract line), referencing the same `customer_key`, plus a `product_number` column (one of `TJN10001`-`TJN10004`, assigned once at random per row when the CSV was generated — not re-randomized on each script run, so the demo scenario is reproducible across resets). `interval_days` (15) and `duration_minutes` are fixed program constants rather than CSV columns, since every line uses the same cadence; `duration_minutes` is set to 45 as a reasonable default (not specified in the request).
  - `start_date` is not stored in the CSV: the script sets every seeded contract line's `start_date` to the date the script runs, so repeated resets always produce a sensible, current visit schedule rather than drifting further into the past each time.
- **Employee product portfolio update, not employee creation.** The script queries all existing employees (ordered by id) and replaces each one's `products` association: every employee gets all four demo products (`TJN10001`-`TJN10004`) except the last employee by id, who gets all but `TJN10004`. This overwrites whatever `employee_products` rows exist today (from `seed.py`'s random assignment or manual edits) — deliberate, since the request specifies portfolios in terms of the whole current employee set.
- **No Google Maps / TomTom involved.** The initial plan assumed reusing "the existing TomTom integration" for addresses, but TomTom is only used for driving-time routing (`tomtom_routing.py`) — geocoding is a separate, already-automatic path (Nominatim via `geocode_address`, triggered by the existing sync). The CSV only needs real street addresses; no geocoding API is called directly by this script or by CSV generation.

## Risks / Trade-offs

- [The script permanently deletes real Tripletex data] → Mitigated only by the `--confirm` flag; it is the operator's responsibility to point this at a demo/test Tripletex account. This is called out explicitly in the proposal and here so it isn't run against a production account by accident.
- [Nominatim's 1 req/sec rate limit means resolving ~150 new customer locations' coordinates via the existing sync will take roughly 2-3 minutes] → Acceptable for an occasional, deliberately-run reset script; not a defect, just an expected runtime cost inherited from the existing geocoding path.
- [Overwriting existing employees' `employee_products` discards whatever manual portfolio adjustments were made before running this script] → Deliberate and scoped to this script only; a normal Admin Portal edit to an employee's products is unaffected.
- [Picking "the last employee by id" as the one without `TJN10004` is arbitrary and shifts if employees are added/removed before a reset] → Acceptable: the request only requires that exactly one employee lack it, not a specific named individual.
- [A customer delete call can fail (observed once against Tripletex's built-in sample company, though a retry later succeeded) and that customer stays behind after a reset] → Accepted as a Tripletex-side limitation outside this script's control, whether permanent (ledger history) or transient; logged and skipped rather than aborting the reset. Re-running the script will retry it.
