## Context

`update_contract_line` (`backend/app/main.py:840-868`) today only updates the `ContractLine` row's own fields — it never touches `ServiceVisit` or `Assignment`. `_delete_service_visits_for_line` (`main.py:688-701`) already exists and deletes every visit (and its assignment) for a line unconditionally, but it's used only by full contract-line/contract deletion — too blunt for this change, which must preserve visits with a started assignment.

The codebase already has the exact vocabulary this change needs, from `assignments`' "An assignment locks automatically once it has started" requirement: an assignment is "started" once `planned_start` has passed, independent of its stored `pinned` flag. `visit_generation.py` already has both date-math primitives this needs: `generate_occurrence_dates(start_date, interval_days, end_date)` (used at creation — includes `start_date` itself as the first occurrence) and `extend_occurrence_dates(furthest_existing, interval_days, new_horizon)` (used by the existing "Extend recurring visits" feature — returns only dates *strictly after* the anchor). Between them they cover both branches this change needs: regenerating from scratch (nothing has started yet) and continuing after a known anchor (something has).

`OPEN_ENDED_HORIZON_DAYS` (currently 90, `visit_generation.py`) is the existing open-ended horizon constant, reused here for consistency rather than introduced as a new concept.

## Goals / Non-Goals

**Goals:**
- Reuse existing primitives (`generate_occurrence_dates`, `extend_occurrence_dates`, the "started" concept) rather than inventing new date math or a new locking concept.
- Never touch a visit with a started assignment, regardless of how the contract line changes.
- Keep the "No end date" checkbox purely a UI affordance — no backend schema or API change, since `end_date: null` already means open-ended.
/
**Non-Goals:**
- No change to the existing "Extend recurring visits" bulk operation — it remains useful for lines that drift toward their horizon without ever being edited.
- No new field marking a visit as "regenerated" or tracking regeneration history — a regenerated visit is indistinguishable from one generated any other way, matching how ad-hoc-booked visits were deliberately left unmarked in an earlier change.
- No attempt to preserve or migrate data on the visits being removed (e.g., copying notes or other visit-level state forward) — today's `ServiceVisit` has no such fields to preserve.
- No change to what counts as "started" itself, or to the pin/unpin API — this change only adds one more code path (contract-line update) that is allowed to remove a not-yet-started assignment, on top of the existing manual "unassign" action.

## Decisions

- **Anchor on the last visit with a started assignment, using its `requested_date`.** This matches how `extend_occurrence_dates` already anchors on a "furthest existing occurrence" date — reusing that exact contract means regeneration and the existing extend-visits feature compute dates the same way, just from different starting points and triggers.
- **Two-branch regeneration**: if a started-visit anchor exists, call `extend_occurrence_dates(anchor_date, new_interval_days, horizon)` (dates strictly after the anchor); if nothing has started, call `generate_occurrence_dates(line.start_date, new_interval_days, horizon)`. Both branches compute `horizon` themselves as `line.end_date or (today + OPEN_ENDED_HORIZON_DAYS)` and pass it explicitly — never relying on `generate_occurrence_dates`'s own internal open-ended default (`start_date + OPEN_ENDED_HORIZON_DAYS`), since for a line whose `start_date` is long in the past that would compute an already-expired horizon. No new pure function needed in `visit_generation.py`.
- **A past `start_date` with nothing started rolls its first occurrence to today, then resumes the original cadence.** Without this, an old, never-touched contract line being edited today would regenerate a whole backlog of overdue visits going back to its original `start_date` — visits nobody will ever staff. Instead: take the full `generate_occurrence_dates(line.start_date, interval_days, horizon)` sequence, keep only the entries strictly after today, and prepend today itself as the first visit. This collapses everything between the original `start_date` and today into one catch-up visit, while every date *after* today still lands exactly where the original cadence would have put it (not restarted from today, which would drift the pattern — e.g. a "every Monday" line would stop landing on Mondays). Only applies when `interval_days > 0` (a one-off line, `interval_days <= 0`, always has exactly one occurrence at `start_date`, unaffected) and when the line hasn't already fully elapsed (`horizon >= today`) — a line whose horizon is already in the past generates nothing, rather than one stray visit beyond its own end.
- **Delete-then-regenerate, not diff-and-patch.** Given `interval_days` itself can change as part of the same edit, old not-yet-started visit dates may not even fall on the new cadence. Deleting everything not-yet-started and generating fresh from the anchor is simpler and always correct, versus trying to reconcile two different cadences.
- **Every contract-line update triggers this, not just changes to the period fields.** The user's request described this as a blanket behavior ("when making changes to the contract lines, I want this pushed to the visits"), and a product-only or duration-only edit still needs its not-yet-started visits to reflect the new terms (visits read products/duration live through the contract line, but existing *assignments* were made assuming the old duration — regenerating clears those too). Scoping the trigger to "only period fields changed" would leave stale assignments in place after a product/duration-only edit, which seems clearly against the intent.
- **Deliberate, narrow override of pin protection.** `assignments`' "Pin an assigned visit" requirement protects a pinned assignment from *schedule runs*. This change adds a second, distinct trigger — an explicit contract-line edit — that is allowed to remove a not-yet-started assignment even if pinned. It does not change what pinning means for schedule runs or manual unassignment; it only adds this one additional path. Flagged explicitly in the proposal and here so it isn't mistaken for an accidental regression later.

## Risks / Trade-offs

- [A planner pins a visit expecting it to be untouchable, then a colleague edits the contract line and it's swept away] → This is the explicit behavior requested; mitigated only by it being a known, spec'd exception rather than a silent side effect. Worth surfacing to end users via product documentation/training, not something this change can enforce further.
- [Editing a contract line to fix a typo in nothing that affects visits (there currently is no such field — every editable field feeds into visit generation or duration) still triggers a full not-yet-started regeneration] → Acceptable: every field on `ContractLineUpdate` (customer_location, dates, interval, duration, products) legitimately affects what future visits should look like, so there's no case where regeneration is truly unnecessary today.
- [The same "backlog of overdue occurrences" problem the past-start_date rollover fixes can also happen in the *anchored* branch — a line whose last started visit was, say, two months ago, on a weekly cadence that was never kept up with, would still generate several weeks of now-past occurrences before reaching a future one] → Deliberately out of scope for this change: the user's request specifically described the no-history case ("no previous visits on the contract line"). The anchored branch's dates come from `extend_occurrence_dates`, unchanged. Worth revisiting as a follow-up if the same backlog issue shows up there in practice.
