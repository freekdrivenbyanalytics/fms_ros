# Design

## Context

`Product`, `Customer`, and `CustomerLocation` (`backend/app/models.py`) currently use Tripletex's own id as their database primary key (`autoincrement=False`) — a deliberate decision from `add-master-data-crud` (archived 2026-09-16), made when "fms_ros is the master" was understood to mean "an entity needs to exist upstream from the moment it's created," so blocking `create_*` on a successful Tripletex push was intentional, not an oversight. That assumption is what this change reverses.

Three concrete symptoms follow directly from the old assumption, confirmed by reading the current code:
- `create_customer`, `create_product`, `create_customer_location` (`backend/app/main.py`) call Tripletex synchronously and raise a `502` if it fails — the row is never created. `update_*` for the same three entities is already local-first with a best-effort push (added later in the same archived change) — only `create` still blocks.
- `main.py`'s `lifespan` handler calls `sync_customers`/`sync_customer_locations` (both full *pulls* from Tripletex) on every backend startup, swallowing failures. Products are not pulled at startup today.
- The only existing "sync" affordance (`/customers/sync`, `/products/sync`, and the frontend's "Refresh from Tripletex" button) pulls Tripletex's data into fms_ros — useful when Tripletex was the master, backwards now that it isn't.

The user was asked how `Product`/`Customer`/`CustomerLocation` should get an id when created without Tripletex, given two realistic options, and chose: **switch to an app-generated primary key plus a separate, nullable `tripletex_id` column** — the same shape `Employee`/`resco_user_id` already uses. This was framed as the higher-risk, more invasive option (implying a full renumbering migration); working through the actual migration mechanics below shows the real risk is much lower than that framing suggested — worth being explicit about, since it changes how big a deal this is.

## Goals / Non-Goals

**Goals:**
- Creating a customer, customer location, or product never fails because Tripletex or Resco is unreachable - it always succeeds locally, with a warning if the push failed.
- A user has a way to *discover* that an entity still needs to be synced (not just a one-time toast they might miss) - a persistent, queryable signal, not only a transient warning.
- The "sync" affordance becomes a bootstrap/reconcile-by-pushing tool: create upstream whatever's missing, update upstream whatever already exists - never pulls upstream data back into fms_ros.
- No Tripletex call of any kind happens automatically at backend startup.
- The whole system - not just backend startup - is verified to work correctly with zero Tripletex connectivity: creating/updating/listing masterdata, generating a schedule, applying it.
- The migration for existing data is additive only: no existing row's `id` changes, so no cascading update to any foreign key anywhere in the schema.

**Non-Goals:**
- Any change to Employee or Assignment sync - `Employee.id` is already app-generated and Assignment has no Tripletex involvement at all; both already match the target shape (local-first, Resco push on create/update, non-blocking).
- Hard delete, anywhere - soft-delete (`archived`) stays the only delete mechanism, unchanged from `add-master-data-crud`.
- Any change to geocoding, region assignment, skills, or service-order-type logic.
- Automatic retry of a failed sync (e.g. a background job that keeps retrying) - the bootstrap-sync button *is* the retry mechanism; no new scheduled/queued retry infrastructure.
- Changing how Resco sync works for customers/locations/products beyond what's needed to make it trigger the same way as employees already do (see Decisions) - the Resco push logic itself (`resco.py`'s `sync_customer`/`sync_customer_location`/`sync_product`) is unaffected.

## Decisions

**Migration is additive - existing rows keep their current `id` unchanged.** For each of `Product`, `Customer`, `CustomerLocation`:
1. Add a nullable, unique `tripletex_id: int | None` column.
2. Backfill `tripletex_id = id` for every existing row (today's `id` already *is* the real Tripletex id for every row that exists, since there was no other way to create one).
3. Change the `id` column from `autoincrement=False` to a proper Postgres identity/sequence column, with the sequence's starting value set above the table's current max `id` (`SELECT setval('products_id_seq', (SELECT MAX(id) FROM products))` or equivalent) - so the very next locally-created row gets a fresh, non-colliding id, and every existing row's `id` (and therefore every foreign key referencing it - `ContractLine.customer_location_id`, `Contract.customer_id`, `contract_line_products`, `*SyncLog.{product,customer,customer_location}_id`, `DrivingTime`'s loosely-typed `(kind, id)` pairs) stays valid with zero rewriting.

This means: **no FK cascade, no row renumbering, no downtime-requiring migration** - the entire migration is two additive columns (well, one per table) plus a sequence adjustment. The "highest risk, most invasive" framing from the earlier question was evaluating the *general* version of this option (which usually does require renumbering); this specific case avoids that because `id` already coincidentally equals what `tripletex_id` needs to be for every row that exists today.

**Going forward, `id` is never populated from Tripletex again, for *any* row - not just locally-created ones.** If a bootstrap sync (see below) or any future pull-like operation ever needs to represent a Tripletex record fms_ros doesn't have locally, it gets a new app-generated `id`, with `tripletex_id` set to Tripletex's id. This is what keeps the two numbering spaces (Tripletex's ids, fms_ros's ids) permanently non-colliding - the moment either space could assign the same `id` value the other already uses, the sequence-starts-above-current-max trick above stops being sufficient. In practice this doesn't come up: per this change's Goals, Tripletex no longer originates new customers/locations/products this system needs to discover, so nothing pulls unknown-to-fms_ros Tripletex records in anymore at all.

**Every Tripletex API call site keyed on `.id` must switch to `.tripletex_id`, and skip (not error) when it's `None`.** `TripletexClient.update_customer(customer.id, ...)`, `create_delivery_address(customer.id, ...)`, `update_product(product.id, ...)`, and the equivalent calls for delivery addresses, all currently assume `.id` is the Tripletex id. Audit every call site in `tripletex.py` and `main.py` (`grep -n "\.id" ` scoped to Tripletex-client call arguments) - each one either becomes `.tripletex_id` (guarded by "only call if not None"), or, for the *create* path specifically, is the call that *sets* `tripletex_id` from the response once it succeeds.

**Warning surfacing: a transient response field, plus a persistent queryable signal - not one or the other.** A one-time toast on the specific create/update request that hit a push failure satisfies the letter of "show a warning," but a user who navigates away before reading it has no way to know an entity still needs syncing. Two pieces, not a new status column:
- `sync_warning: str | None = None` added to `CustomerOut`/`ProductOut`/`CustomerLocationOut`, populated only in the response of the specific request that just attempted (and partly or fully failed) a push - e.g. `"Sync to Tripletex failed - retry from Sync to Tripletex."` Never persisted, never present on a plain `GET`.
- The *persistent* signal already exists for free: `tripletex_id is None` (never yet synced to Tripletex) and `resco_*_id is None` (never yet synced to Resco) are exactly "still needs syncing," queryable and already part of the data model. The frontend list views show a badge/indicator driven by these two fields - not a new backend concept, just surfacing existing nullable columns that today aren't shown at all.

**The bootstrap-sync endpoints keep their existing URLs and button placement, but their implementation is fully replaced.** `POST /customers/sync` (bundles customer + customer-location reconciliation, matching today's UX) and `POST /products/sync` stay where they are; `sync_customers`/`sync_customer_locations`/`sync_products` (the pull functions) are replaced by new push functions with the same names' *intent* but the opposite direction: iterate non-deleted, non-archived local rows; for each with no `tripletex_id`, create upstream and store the returned id; for each with one, push current local values as an update. Frontend button copy changes from "Refresh from Tripletex" to something reflecting the new direction (e.g. "Sync to Tripletex") - this is a real, user-visible behavior change and should read as one, not be silently relabeled to look unchanged.

**Bootstrap sync must push customers before their locations, within the same run.** A customer location's Tripletex delivery-address create needs its customer's Tripletex id; a customer not yet synced this run (no `tripletex_id` before this sync started) needs to be created *first*, in the same bootstrap-sync call, so its newly-returned `tripletex_id` is available when that customer's locations are processed next - not two independent passes where a location silently gets skipped because its customer "isn't synced yet" when it actually would be by the end of this same run. Implementation-wise: process all customers to completion, then all locations, within one request/function - not two separately-triggerable operations that happen to usually run back to back.

**Exception handling in the new local-first create paths must be broad, not just `TripletexAuthError`.** The existing blocking `create_*` endpoints only catch `TripletexAuthError` specifically (auth/session failures) and let anything else (timeout, connection refused, 500 from Tripletex) propagate as an unhandled `500`. The already-correct `update_*` endpoints catch `Exception` broadly and log a warning. The new create paths must match that broader pattern - "Tripletex is unreachable" covers more failure modes than "the session token is bad," and this change's whole point is that none of those failure modes should prevent local creation.

**Verifying point 5 needs an explicit, positive test, not just a code read.** Point-in-time plan: with a deliberately invalid/unreachable Tripletex base URL configured, restart the backend and confirm it starts cleanly (no startup sync to fail); create a customer, a customer location, and a product, confirming each succeeds locally with a sync warning; update each, confirming the same; generate and apply a schedule end to end, confirming nothing in that path touches Tripletex at all (it shouldn't - route-optimization has no Tripletex dependency today, but this is exactly the kind of assumption worth confirming rather than asserting). This is a manual verification task, not just an automated-test claim.

**`reset_demo_data.py` gets reworked to local-first, not left on a special-cased pull path - found live during implementation.** Its current flow creates customers directly in Tripletex, then relies on the old `sync_customers`/`sync_customer_locations` to pull them into local rows, and (load-bearing) assigns each local `CustomerLocation.id` from the Tripletex delivery-address id the create call returned - a comment in the code says so explicitly. Once `id` is fms_ros-assigned and `sync_*` is push-only, this breaks outright for every seeded row. The user chose reworking it over keeping a separate pull path alive just for this script (rejected: two divergent sync mental models coexisting is worse than one script's extra rewrite). New flow: create each CSV row's customer and its first customer location *locally* (direct ORM inserts, fms_ros-assigned ids, no Tripletex call yet) - contracts/contract lines/service visits then seed immediately against those local `CustomerLocation` objects directly, with no more customer-key → Tripletex-id → local-id indirection needed at all (a simplification: the script already has the local objects in hand right after creating them, it no longer needs to re-fetch them by an id it doesn't control the meaning of); the Tripletex/Resco push happens last, via the new bootstrap-sync functions, after all local seeding (customers, locations, contracts, lines, visits) is complete. See the `demo-data-reset` spec delta for the corresponding requirement changes.

**`/customers/sync` tightened to admin-only, and the Customer Portal's non-admin "Refresh" control removed - a second dependent found live during implementation.** `frontend/src/customer-portal/CustomersView.tsx` has a "Refresh" button, available to any logged-in customer-portal user (not gated by `isAdmin` - confirmed by reading `CustomerPortalApp.tsx`'s render logic), that calls `syncCustomers()` → `POST /customers/sync`. That endpoint is becoming a real upstream-write operation (creates/updates records in the connected Tripletex/Resco account for every customer in the system, not scoped to the calling user's own customers) - letting any authenticated customer trigger that is a real authorization gap, not just a stale label. Presented three options (remove the control; keep it as a harmless local-only reload with no Tripletex call; keep it calling the real endpoint but admin-gate the control) - user chose removal outright, since under local-first there's nothing left to meaningfully refresh (the portal's own `listCustomers`/`listCustomerLocations`/`listContracts` calls already reflect current truth, no sync of any kind needed). `/customers/sync`'s own FastAPI dependency changed from `require_session` to `require_admin` to match `/products/sync`'s existing convention, closing the gap at the API layer too (not just by removing the one known caller) - see the `customer-portal` spec delta for the removed requirement.

## Risks / Trade-offs

**Staff used to "Sync to Tripletex" meaning "pull Tripletex's changes in" will get a behaviorally opposite operation with a similar-looking button.** → Explicit copy change (not just a silent implementation swap), called out as **BREAKING** in the proposal, and worth a short heads-up to whoever uses that button today before this ships.

**The persistent "not yet synced" signal (`tripletex_id`/`resco_*_id` being null) says nothing about *why* a sync failed, only *that* it hasn't succeeded yet.** A transient auth failure and "this entity has never been synced because it's brand new and the sync hasn't been run yet" look identical in the persistent signal. → Acceptable for this change: the bootstrap-sync button retries regardless of cause, and the transient `sync_warning` on the triggering request is where cause-specific detail belongs. A richer per-entity sync-history/error-log is a reasonable future change if this turns out to matter, not built here.

**This change touches three entity types' core identity handling at once** (schema, every Tripletex call site, every create/update endpoint, the sync endpoints, the relevant frontend views) - a wide blast radius for one change. → Mitigated by the migration being additive/zero-cascade (see Decisions), and by `add-master-data-crud`'s prior work already having established the target shape for *update* - this change is extending an already-proven pattern to *create*, plus the schema/direction change, not inventing the pattern from scratch.

**The connected Tripletex API credentials currently lack customer-create permission - found live during manual verification (task 10.5).** A scoped live test (one throwaway local customer, pushed via the exact same call `sync_customers` makes for a missing-`tripletex_id` row) got a real `403 "You do not have permission to access this feature"` from Tripletex, not a network/auth failure. This is a characteristic of the currently configured API credential/account, not a bug in this change - the code handled it exactly as designed (local row unaffected, would surface as a `sync_warning` on the real endpoint, no partial Tripletex-side resource left behind since the create call failed before anything was created). → No code change from this; flagged so the user can grant the Tripletex integration credential customer-create permission if they want the create-side of the bootstrap push (and local-first customer creation's Tripletex push) to actually succeed against the real account. Until then, every customer create/bootstrap-push will report a Tripletex `sync_warning` (Resco still succeeds independently, confirmed live in the same verification pass) - which is itself the correct, intended behavior for an unreachable/unauthorized upstream, just worth knowing the specific cause here isn't network unreachability.

## Migration Plan

1. Alembic migration: add `tripletex_id` (nullable, unique) to `products`, `customers`, `customer_locations`; backfill `tripletex_id = id` for every existing row in each; adjust each table's `id` sequence to start above its current max value; change `id`'s column definition to use that sequence (identity/serial) going forward. No FK changes, no data loss, no downtime-requiring lock beyond a normal `ALTER TABLE ADD COLUMN`.
2. Code changes land together with the migration (a schema change and the code that depends on it shouldn't ship separately): every `.id`-as-Tripletex-id call site, the three `create_*` endpoints, the sync endpoints/functions, the `lifespan` startup handler, the `*Out` schemas.
3. Frontend changes (button copy, warning display, sync-status badges, anywhere `id` was shown as if it were "the Tripletex ID") land in the same change, since the backend response shape (`tripletex_id` field, `sync_warning` field) is new.
