# Proposal

## Why

`add-master-data-crud` (archived 2026-09-16) deliberately made creating a customer, customer location, or product **block on a successful Tripletex push** — because at the time, "fms_ros is the master" meant an entity needed to exist upstream from the moment it was created. That assumption no longer holds: this portal is now the master for masterdata, and Tripletex/Resco are downstream systems it feeds, not systems it depends on to function. Today three concrete problems follow directly from the old assumption: creating a customer/location/product still fails outright if Tripletex is unreachable; the backend still pulls from Tripletex on every startup even though nothing depends on that pull completing; and the existing "sync" buttons pull changes *from* Tripletex, the opposite of what's actually needed now (pushing this portal's own data out to bootstrap an empty or lagging Tripletex/Resco).

## What Changes

- **BREAKING**: `Product`, `Customer`, and `CustomerLocation` switch from a Tripletex-sourced primary key to an app-generated primary key plus a separate, nullable `tripletex_id` column (the same shape `Employee`/`resco_user_id` already uses) - additive migration, no existing row's `id` value changes (see design.md's Migration Plan).
- Creating a customer, customer location, or product no longer blocks on Tripletex: the entity is persisted locally first (adopting a locally-generated id immediately), then the system attempts to push it to Tripletex and Resco. A push failure does not fail the create; the response carries a warning explaining that the Tripletex/and-or Resco sync failed and needs to be retried.
- Updating one of these three entities already pushes to Tripletex/Resco best-effort without blocking (`add-master-data-crud`'s existing behavior) - this change adds the same warning-surfacing on push failure there too, so create and update behave consistently.
- **BREAKING**: the existing "sync"/"Refresh from Tripletex" buttons and their backend endpoints, which currently *pull* Tripletex's/Resco's data into fms_ros, are replaced with a *push*-based bootstrap-reconcile operation: for each local entity with no `tripletex_id` (and/or no Resco id), create the corresponding record upstream and store the returned id(s); for each entity that already has one, push its current local values to update the corresponding upstream record. Intended use: bootstrapping an empty (or out-of-date) Tripletex/Resco org from this portal's existing data, not pulling upstream changes back in.
- The backend no longer runs any Tripletex sync automatically at startup - the current `sync_customers`/`sync_customer_locations` calls in the FastAPI `lifespan` handler are removed entirely (products already don't sync at startup today).
- Audit and confirm every core workflow - backend startup, listing/creating/updating masterdata, generating and applying a schedule - functions correctly with Tripletex completely unreachable, not just "degrades gracefully at startup" as today's spec already promises for the pull-sync path.
- **BREAKING, found during implementation, not in the original request**: `backend/app/reset_demo_data.py` (the `demo-data-reset` capability) depends entirely on the old pull semantics - it creates customers directly in Tripletex, then relies on the old `sync_customers`/`sync_customer_locations` to pull them locally and (load-bearing) assigns each local `CustomerLocation.id` from the returned Tripletex delivery-address id. Once `sync_*` becomes push-only and `id` is fms_ros-assigned, this script fails outright (`db.get(CustomerLocation, location_id)` returns `None` for every seeded row). Reworked to be local-first too: create customers/locations locally first (immediate fms_ros-assigned ids, no indirection through Tripletex), seed contracts/lines/visits against those local rows directly, then push everything to Tripletex at the end via the new bootstrap-sync functions - see design.md's Decisions and the `demo-data-reset` spec delta.
- **BREAKING, found during implementation, not in the original request**: the Customer Portal's own Customers view (`frontend/src/customer-portal/CustomersView.tsx`) has a "Refresh" control, available to *any* logged-in customer-portal user (not admin-gated), that calls the same `/customers/sync` endpoint being repurposed into a push. Under local-first there's nothing left to usefully "refresh" (the portal's own data no longer drifts from Tripletex), and letting a non-admin user trigger writes to the connected Tripletex/Resco account for the whole system would be a real authorization regression. Removed entirely (user's explicit choice, over keeping it as a harmless local-only reload or admin-gating it in place) - see the `customer-portal` spec delta.

## Capabilities

### Modified Capabilities
- `customers`: "Customer data model", "Customer location data model" (add `tripletex_id`, redefine what "system of record" means for identity), "Create, update, and soft-delete a customer" and the customer-location equivalent (local-first, warning on push failure), "Customers are synced from Tripletex" and "Customer location sync triggers" (pull-based sync replaced by the push-based bootstrap operation; startup trigger removed)
- `products`: "Product data model" (add `tripletex_id`), "Sync products from Tripletex" (replaced by push-based bootstrap), "Create, update, and soft-delete a product" (local-first, warning on push failure)
- `resco-integration`: "Customers and customer locations sync to Resco automatically after a Tripletex sync" (currently framed around "at backend startup or on demand" - startup no longer applies; automatic Resco sync now also follows the new local-first create path, not only update)
- `demo-data-reset`: reseed order inverted - customers/locations are created locally first (immediately usable, fms_ros-assigned ids), contracts/lines/visits seed against those local rows directly, and the push to Tripletex happens last, reusing the new bootstrap-sync functions instead of the old pull
- `customer-portal`: "Refresh customers from Tripletex" removed - the underlying pull no longer exists, and the control was available to non-admin users, which is no longer appropriate once `/customers/sync` triggers real upstream writes

## Impact

- `backend/app/models.py`: `tripletex_id` column on `Product`, `Customer`, `CustomerLocation`; PK generation strategy change (see design.md).
- A new Alembic migration: additive column + backfill + PK sequence change, no data loss, no FK changes needed (existing `id` values are untouched).
- `backend/app/tripletex.py`: every call site that sends `.id` to a Tripletex API (update/create-delivery-address calls) must send `.tripletex_id` instead; the pull-based `sync_customers`/`sync_customer_locations`/`sync_products` functions are replaced by new push-based bootstrap functions.
- `backend/app/main.py`: `create_product`/`create_customer`/`create_customer_location` become local-first with best-effort push; `lifespan` startup sync calls removed; `/customers/sync`, `/products/sync` (and any customer-location equivalent) repointed at the new push-based bootstrap logic.
- `backend/app/schemas.py`: `tripletex_id` added to the relevant `*Out` schemas; a transient warning field added to surface a push failure from the specific create/update request that hit it.
- `backend/app/resco.py`: likely unaffected in its own logic (Resco already keys off its own `resco_*_id` columns, never `.id`), but its callers change per the above.
- `backend/app/reset_demo_data.py`: reordered to local-first (see the added bullet above and the `demo-data-reset` spec delta).
- `backend/app/main.py`: `/customers/sync` tightened from session- to admin-level auth (see design.md's Decisions) - it now triggers real upstream writes, not a read-oriented reconciliation.
- Frontend (`frontend/src/admin-portal/...`): "Refresh from Tripletex"-style button copy/behavior updated to reflect the new push direction; a warning/toast surfaced when a create or update response carries a sync warning; anywhere the UI currently shows `id` as if it were "the Tripletex ID" needs to show `tripletex_id` instead.
- Frontend (`frontend/src/customer-portal/CustomersView.tsx`, `CustomerPortalApp.tsx`): the customer-portal "Refresh" control and its `syncCustomers()`/`handleRefresh` wiring removed entirely (see the added bullet above).
