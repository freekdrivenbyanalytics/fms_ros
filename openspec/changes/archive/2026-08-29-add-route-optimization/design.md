## Context

The backend (`backend/app/main.py`) already exposes everything the optimizer needs to read: `GET /employees` (with regions/skills), `GET /service-visits` (with contract, required skills, customer location, region), and `GET /assignments`. `Employee` and `CustomerLocation` already carry latitude/longitude (used today only for display, e.g. in the Customer Portal). There is no routing/optimization dependency anywhere in the stack today, and no precedent in this repo for a third backend-side service — the closest analogue is the Tripletex integration, which calls an external SaaS over HTTP from `backend/app/tripletex.py`; this instead runs a service *we* host. See proposal.md - Why / What Changes for motivation and scope; see specs/route-optimization/spec.md for required behavior.

## Goals / Non-Goals

**Goals:**
- Keep the new solver service's HTTP contract simple enough that the domain-model choice inside it (see Decisions) can change later without touching the backend or frontend.
- Keep proposals ephemeral — no new database table, no persistence of a "pending proposal" — consistent with "generating a proposal creates no assignment."
- Keep the solver service reachable only from the backend, never directly from the browser, mirroring how Tripletex credentials/traffic stay server-side.

**Non-Goals:**
- No true continuous vehicle-routing sequencing across multiple days for one employee — see the modeling decision below; travel-distance minimization is per employee per day, not a single global route.
- No persistence, history, or comparison of past optimization runs — each run is independent and stateless.
- No partial/selective apply in this version (confirmed) — applying commits every schedulable visit in the proposal at once.
- No authentication/authorization on the new endpoints, consistent with the rest of the app today.

## Decisions

- **A new standalone `solver/` service** (its own directory, `requirements.txt`, and process — not embedded in `backend/`), per the confirmed architecture choice. It exposes one HTTP endpoint, `POST /optimize`, built with FastAPI for stack consistency, and depends on Timefold's Python solver library. Alternative considered: embed the solver directly in the existing FastAPI backend — rejected per the explicit "New standalone solver microservice" decision, and because Timefold's solve loop is CPU-bound and long-running, which is cleaner to isolate in its own process regardless.
- **Confirmed via a live discovery spike (`solver/discovery_spike.py`)**: the real PyPI package is `timefold` (not `timefold-solver`, an older/lower-versioned package under the same organization). Its Python API is annotation-based on plain dataclasses — `id: Annotated[str, PlanningId]`, `employee: Annotated[Employee | None, PlanningVariable(value_range_provider_refs=["employee_range"])]`, collections via `Annotated[list[X], PlanningEntityCollectionProperty]` / `ValueRangeProvider(id=...)`, and the solution's score via `Annotated[HardSoftScore | None, PlanningScore]` — not the decorator/method-based shape originally guessed here. `PlanningVariable(allows_unassigned=True)` is a real, direct parameter, confirming the "visit may stay unscheduled" requirement is natively supported. **Critically, `timefold` is a Java library wrapped via JPype, not pure Python — it requires a JVM at runtime.** This was not anticipated before implementation; see Risks. Mitigation: `jdk4py` (a pip-installable package that bundles an actual JDK binary) is added as a pinned solver-service dependency so no system-wide Java install is required — `os.environ["JAVA_HOME"]` and `PATH` (the JDK's `bin` directory specifically, or native library loading fails with a "Can't find dependent libraries" error even though the JDK is otherwise functional) must be set from `jdk4py.JAVA_HOME` before importing `timefold`. JDK 21 (LTS) is used, not the newest JDK 25 build `jdk4py` also offers, for broader compatibility with JPype 1.5.1.
- **Two more findings from a second, fuller spike (`solver/discovery_spike2.py`)**: (1) `frozenset[str]`-style parameterized generic collection type hints on dataclass fields (e.g. for skill/region id sets) crash Timefold's Java-side deep cloner with a reflection error; plain unparameterized `frozenset` works. (2) With `allows_unassigned=True` and only `HardSoftScore`, the solver has no incentive to actually schedule a visit when leaving it unassigned already scores a feasible 0 — it needs a third score level. Switching to `HardMediumSoftScore` (hard = constraint violations, medium = one penalty per unassigned visit via `for_each_including_unassigned`, soft = travel-distance minimization) fixes this and matches Timefold's own documented pattern for "prefer full assignment, then optimize a secondary objective." Verified end-to-end: skills, region, working hours, and travel distance all produce correct results against a small synthetic dataset.
- **Domain model: a plain assignment-style model, not a chained/list-variable route model.** Each currently-unassigned visit is a planning entity with two planning variables: which employee (`allows_unassigned=True` lets a visit stay unscheduled if no feasible employee exists) and a planned start time, drawn from a discretized set of candidate times (e.g. 15-minute increments) within the intersection of the visit's requested date and the employee's working hours. Travel-distance minimization is computed as a soft constraint via grouping: for each (employee, date) pair, sort that employee's scheduled visits (existing + proposed) by planned start and sum the haversine distance between consecutive stops. Alternative considered: Timefold's chained/list-planning-variable vehicle-routing model (its documented approach for exactly this kind of problem, with shadow variables tracking arrival time) — confirmed real and available in this API (not yet spiked), but deliberately deferred: the simpler assignment-style model above is now confirmed working end-to-end, and switching models mid-implementation would discard that verified foundation. Revisit with a proper routing model in a later change once the team has hands-on Timefold experience.
- **Confirmed via `solver/verify_domain.py`** (a scripted run of the real `solver/app/domain.py` + `solver/app/constraints.py` against `SolverFactory`, not a spike file): the cross-class overlap/distance constraints against `ExistingAssignmentFact` — `constraint_factory.for_each(VisitAssignment).join(ExistingAssignmentFact, Joiners.equal(left, right), Joiners.equal(...), Joiners.overlapping(v_start, v_end, e_start, e_end))` — work exactly as the two-and-four-argument `Joiners` signatures suggested. This was the one construct the discovery spikes hadn't exercised. A 3-visit/2-employee/1-existing-assignment scenario solved with 0 hard violations: a visit needing a skill nobody has was correctly left unassigned (medium penalty only) rather than forced into a skill or overlap violation, and the visit assignable to the employee with the pre-existing booking was scheduled to start exactly when that existing assignment ends, not overlapping it.
- **Existing assignments are problem facts, not planning entities** — they're included in the solver's input so the constraint provider can check the no-overlap constraint against them and factor them into per-employee-per-day travel distance, but the solver never changes their employee or time, per specs' "A schedule run never alters existing assignments."
- **Proposals are ephemeral and client-held.** `POST /optimize/propose` returns the full proposal to the caller; nothing is persisted server-side. The frontend holds the proposal in memory and sends it back verbatim to `POST /optimize/apply` when the planner applies it. Alternative considered: persist a "proposal" row so `apply` only needs a proposal id — rejected as an unnecessary schema addition for a value that's only ever used once, immediately, by the same browser session that generated it.
- **`apply` re-validates only that each visit is still unassigned** (the same invariant `POST /assignments` already enforces), reusing that endpoint's underlying logic rather than duplicating it. It does not re-validate the proposal's skill/region/hours correctness against current data — see Risks for the trust-model trade-off this implies.
- **HTTP contract** between backend and solver service: request carries employees (id, work hours, lat/long, skill ids, region ids), unassigned visits (id, requested date, duration, required skill ids, region id, lat/long), and existing assignments (employee id, planned start/end); response carries scheduled visits (visit id, employee id, planned start/end) and any visit ids left unscheduled. A configurable `SOLVER_TIME_LIMIT_SECONDS` (backend setting, passed to the solver service) bounds how long a solve run may take before returning its best-found solution, since this is a synchronous HTTP call from the backend's perspective.
- **Frontend**: a new "Optimize" view, a third option in `App.tsx`'s existing view switch (alongside Manual Assignment and Day Planning) — reuses that existing pattern rather than introducing a new navigation mechanism.

## Risks / Trade-offs

- [Timefold's Python package requires a JVM at runtime (via JPype), not anticipated before implementation] → Resolved via the task 1 discovery spike: `jdk4py` bundles a pinned, pip-installable JDK so no system-wide Java install is needed; `JAVA_HOME`/`PATH` must be set from it before importing `timefold` (see Decisions). This does mean the solver service's own setup is a bit more involved than a typical pure-Python service — worth calling out clearly in the README (task 5.2).
- [The assignment-style model with discretized start times is less rigorous than a true chained route model — travel-distance minimization is a grouped approximation, not a native routing objective] → Accepted for this version; the hard constraints (skills/region/hours/no-overlap) hold regardless, and the softer travel-distance objective can be revisited with a proper list-variable model later.
- [A synchronous solve could be slow for a large number of unassigned visits] → Mitigation: `SOLVER_TIME_LIMIT_SECONDS` bounds run time; acceptable dataset sizes for this POC are small.
- [Applying a proposal doesn't re-check skills/region/hours, so a tampered client payload could create an assignment that violates them] → Accepted for this POC (no auth/roles exist anywhere yet); worth revisiting once real authorization is added.
- [A fourth local process adds real setup friction for anyone running this locally] → Mitigation: extend `start-dev.ps1` to also launch the solver service, and document manual startup in the README alongside the existing backend/frontend steps.

## Migration Plan

1. Discovery (task 1): scaffold `solver/`, install the real Timefold Python package, and confirm a trivial constraint provider solves against a synthetic 2-employee/2-visit dataset.
2. Build the real domain model and constraints (skills, region, working hours, no-overlap, travel distance, requested-date-fixing) per specs/route-optimization/spec.md.
3. Wire the backend: `SOLVER_BASE_URL`/`SOLVER_TIME_LIMIT_SECONDS` settings, `backend/app/solver_client.py`, `POST /optimize/propose` and `POST /optimize/apply`.
4. Build the frontend Optimize view and wire it into `App.tsx`'s view switch.
5. Update `start-dev.ps1` and the README to cover the new service.
6. Rollback: the new service and endpoints are additive — removing them (or simply not running the solver service) leaves the existing manual-assignment and Day Planning flows fully unaffected, since no database schema changed.
