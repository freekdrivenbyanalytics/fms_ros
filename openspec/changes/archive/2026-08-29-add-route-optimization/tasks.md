## 2. Solver Domain Model and Constraints

- [x] 2.1 Define the planning entity (unassigned visit, with employee and planned-start-time planning variables) and problem facts (employees, existing assignments) per design.md's domain model decision. (`solver/app/domain.py` — `Employee`/`ExistingAssignmentFact` problem facts, `VisitAssignment` planning entity with `employee`/`start_minutes` planning variables (`allows_unassigned=True`), `Schedule` planning solution. `requested_date` is a fixed field, never a planning variable, so a visit's date can't drift from what was requested.)
- [x] 2.2 Implement the hard constraint: assigned employee possesses every skill the visit's contract requires. (`solver/app/constraints.py` — "Missing required skill".)
- [x] 2.3 Implement the hard constraint: assigned employee is scoped to the visit's region. (`solver/app/constraints.py` — "Employee not scoped to region".)
- [x] 2.4 Implement the hard constraint: the visit's proposed time window falls within the employee's working hours, and its planned start stays on the visit's requested date. (`solver/app/constraints.py` — "Outside working hours"; the requested-date part is structural per 2.1, not a separate constraint.)
- [x] 2.5 Implement the hard constraint: no time overlap between an employee's proposed and existing visits, or between two visits proposed to the same employee. (`solver/app/constraints.py` — "Overlapping proposed visits" via `for_each_unique_pair` + `Joiners.equal`/`Joiners.overlapping`, and "Overlapping existing assignment" via a cross-class `.join(ExistingAssignmentFact, ...)` with a 4-arg `Joiners.overlapping`. This cross-class join was the one pattern not covered by the discovery spikes — verified working via `solver/verify_domain.py`, a small scripted scenario run against the real `app.domain`/`app.constraints` modules with `SolverFactory`, confirming 0 hard violations and correct overlap-avoidance against a problem-fact existing assignment.)
- [x] 2.6 Implement the soft constraint: minimize total travel distance per employee per day across that employee's existing and proposed visits (grouped and sorted by planned start, per design.md). (`solver/app/constraints.py` — "Travel distance between proposed visits" and "Travel distance to existing assignment", both pairwise-haversine per (employee, date) rather than a literal sorted-route sum, matching design.md's "grouped approximation" decision.)
- [x] 2.7 Allow a visit to remain unscheduled when no feasible assignment exists, and include unscheduled visit ids in the response. (`allows_unassigned=True` on both planning variables plus the "Unscheduled visit" medium constraint in `solver/app/constraints.py`, so leaving a truly infeasible visit unassigned is preferred over a hard-constraint violation; verified in `solver/verify_domain.py` with a visit requiring a skill nobody has.)
- [x] 2.8 Add `SOLVER_TIME_LIMIT_SECONDS` handling so a solve run returns its best-found solution after a bounded time. (`solver/app/schemas.py` — `OptimizeRequest.time_limit_seconds` (optional, defaults to `DEFAULT_TIME_LIMIT_SECONDS = 30`); `solver/app/solve.py` — `TerminationConfig(spent_limit=Duration(seconds=time_limit_seconds))`. `solver/app/main.py` rewired off its task-1.1 stub onto `POST /optimize` → `solve_schedule()`; verified end-to-end by calling `solve_schedule()` directly with a 2-employee/2-visit/1-existing-assignment `OptimizeRequest` — produced the same correct schedule as `solver/verify_domain.py`.)
