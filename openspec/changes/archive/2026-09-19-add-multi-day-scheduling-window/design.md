# Design

## Context

`solver/app/domain.py`'s `VisitAssignment` currently has two planning variables - `employee` and `start_minutes` (a shared `start_time_range` of 06:00-20:00 in 15-minute steps) - and a *fixed* `requested_date` field the solver never touches. `backend/app/solver_client.py`'s `_visit_payload` sends `effective_schedule_date(visit)` (the visit's own `requested_date`, floored to today if already passed) as that fixed date, before the solver ever runs. Every constraint in `constraints.py` that needs to know "is this employee free that day" or "are these two visits on the same day" joins on that fixed `requested_date` - `_same_employee_same_date`, `_same_employee_same_date_cross`, `_visit_employee_id_same_date_schedule`, `_first_visit_of_day_joiners`.

Service visits are generated at fixed intervals per contract line (`backend/app/visit_generation.py`'s `step_occurrence`/`generate_occurrence_dates`, called from wherever visits get created/extended) - each `ServiceVisit.requested_date` is a real, calendar-correct occurrence of that contract line's cadence (`interval_unit`/`interval_count`: week/1-4, month/1-3, or quarter/1), anchored to the contract's own start date, independent of how any individual visit ends up actually scheduled. `backend/app/models.py`'s `Assignment` records the actual outcome (`planned_start`/`planned_end`), which can diverge from the visit's nominal `requested_date` once a visit has been rescheduled.

Investigated live: on the current dev data, `_load_run_data` already loads *every* `ServiceVisit` row (`db.query(ServiceVisit)...all()`, no date filter) into Python before windowing - so finding a visit's sibling occurrences for the same contract line needs no new query, just grouping already-in-memory data by `contract_line_id`.

**A pre-existing bug found while reading this code, fixed as part of this redesign** (see proposal.md): `_existing_assignment_payload`'s date field is sourced from `assignment.service_visit.requested_date` (the visit's nominal date), not `assignment.planned_start.date()` (the date the assignment actually occupies). These only diverge for a visit that was overdue when it got scheduled, but when they do, same-day joins against that locked assignment silently use the wrong date. This redesign's `ExistingAssignmentFact` needs a field with exactly the corrected semantics ("the date this fact actually occupies") to join against the new `VisitAssignment.date`, so the fix falls out of doing this properly rather than being separate work.

## Goals / Non-Goals

**Goals:**
- The solver may place a visit on any date within the run's scheduling window (never before today, never outside the window), not only its own nominal date - enabling the cross-day trade-offs day-by-day chaining structurally cannot make (see proposal.md's Why).
- Two new soft preferences keep that freedom from being a free-for-all: stay close to the visit's own nominal date, and don't compress the interval since the contract line's previous *nominal* occurrence (not wherever that occurrence actually landed).
- Every existing hard constraint (skills, region, working hours, double-booking, driving-time gaps) continues to hold for whichever date the solver picks - no change to what "feasible" means, only to what "date" means as an input to those checks.

**Non-Goals:**
- No change to `days_until_due`/priority-tier weighting for unscheduled visits (`_unscheduled_priority_weight` in `constraints.py`) - that scoring is already carefully tuned (see its own extensive comments) around `days_until_due` staying bounded at `_URGENCY_CAP`, and this change doesn't touch it. An overdue visit's urgency stays tied at max, exactly as today.
- No change to the `parallel` execution mode's region-grouping (`group_regions_by_shared_employees`) - it partitions by region/employee, an orthogonal axis to date, and needs no changes for this to work correctly within each group.
- No per-visit custom date value ranges (e.g. bounding a visit's own range to its true contract window). Considered and rejected in favor of one shared range across the whole run's window (see Decisions) - simpler, and the two soft preferences already discourage inappropriate drift without needing a hard per-visit bound.
- No change to how visits are generated (`visit_generation.py`) or to contract line intervals themselves.

## Decisions

**A new `date` planning variable, not a repurposed `requested_date`.** `VisitAssignment` keeps `requested_date` as the fixed, never-mutated nominal (contract-cadence) date - the anchor the new preferences measure against - and gains a new mutable `date: date | None` variable (`PlanningVariable(value_range_provider_refs=["date_range"], allows_unassigned=True)`) that the solver actually chooses. Every constraint that currently groups by `requested_date` for "same day" purposes switches to `date` instead; `requested_date` is now read only by the new nominal-date-preference constraint.

**One shared `date_range` value-range across the whole run, not a per-visit bounded range.** Timefold supports per-entity custom value ranges, but it's a more advanced, less-used pattern in this codebase than a single `ValueRangeProvider` on `Schedule` (exactly how `start_time_range` already works). A shared range (every date in the run's scheduling window, i.e. `days_ahead` consecutive dates starting today) keeps the model consistent with the existing style and lets the two soft preferences - not a hard per-visit bound - do the work of discouraging inappropriate drift, matching what was agreed: never a hard forbid, only a growing preference against it.

**The previous-occurrence link is precomputed in Python at payload-build time, not resolved by the solver via a fact join alone.** For each candidate visit, `backend/app/solver_client.py` finds its contract line's immediately preceding `ServiceVisit` (by `requested_date`, among the already-loaded `all_visits` - no new query) and determines which of two cases applies:
- The previous occurrence is *also* a candidate in this run (unassigned, or assigned-but-unpinned - i.e. it's also getting its own `date` decided this run): send `previous_visit_id` (that sibling's id). The interval constraint then joins `VisitAssignment` to `VisitAssignment` and compares their *chosen* `date` variables - genuinely joint reasoning, since neither date is fixed yet.
- The previous occurrence has a locked assignment (pinned, already started, or otherwise not a candidate this run): send `previous_actual_date` as `None` and instead `previous_nominal_date`... - no: send the fixed comparison value directly, sourced from that locked assignment's *own* `requested_date` fact (not its actual applied date - see the "nominal, not actual" decision below), via a `VisitAssignment`-to-`ExistingAssignmentFact` join, mirroring the existing pattern of a "between two proposed visits" constraint plus a "proposed vs. existing assignment" constraint (see `driving_time_gap_between_proposed_visits` / `driving_time_gap_to_existing_assignment`).
- No previous occurrence exists at all (first occurrence of its contract line): both `previous_visit_id` and the existing-assignment lookup find nothing; the interval constraint simply doesn't fire for that visit (`interval_days` is `None`).

Also computed the same way, no new query: `interval_days` - the number of days between this visit's own `requested_date` and its previous occurrence's `requested_date`. Taken from the real generated dates rather than recomputed from `interval_unit`/`interval_count`, since month/quarter intervals aren't a fixed day-count (`add_calendar_months` already handles that correctly at generation time - reusing the generated dates sidesteps reimplementing that logic).

**The interval preference measures from the previous occurrence's *nominal* date, never its actual date.** This is the load-bearing decision from the business discussion that produced this design: anchoring to an actual (possibly already-delayed) date would let one delay license the next occurrence to drift further, compounding indefinitely and quietly reducing how many visits a contract line actually receives over a year. Anchoring to the fixed nominal cadence means every occurrence is independently pulled back toward the contract's real schedule, regardless of what happened to its neighbors.

**Nominal-date preference outweighs the interval preference.** Confirmed by the worked example in the proposal discussion (a contract starting Jan 1, biweekly, where visit 1 slips to Jan 3): visit 2's nominal date is Jan 15 (from the contract's fixed cadence, unaffected by visit 1's slip) - if Jan 15 has capacity, the solver should take it even though only 12 days will have passed since visit 1's actual date, because sitting exactly on-schedule outweighs the smaller interval-compression penalty. Only when Jan 15 has no feasible placement does the interval preference meaningfully steer the choice among the remaining dates, nudging toward Jan 18 (14 days after visit 1's actual Jan 3) over an arbitrarily-close alternative. Implemented as two constraints in the *same* soft tier with a weight ratio (nominal-date weight noticeably larger per day of drift than interval-shortfall weight per day of compression) rather than separate score tiers - simpler than introducing a fourth score level, and sufficient to reproduce the worked example. The exact ratio is a tuning question (see Risks) - implementation should start from a conservative ratio (e.g. 10:1) and adjust based on real results, not treat the first value chosen as final.

**`employee_day_schedules` must cover every date in the run's window per employee, not just the dates visits happen to nominally fall on.** Today, `_load_run_data`'s `candidate_dates` is the sparse set of dates that actually appear among `ready_visits`' effective dates - fine when date is fixed, since the solver only ever needs schedules for those exact dates. Once `date` is a free variable, the solver may want to place a visit on *any* day in the window, so every employee's working-hours window for every day in `[today, today + days_ahead - 1]` must be sent, or the "no resolved schedule for this date" hard constraint would incorrectly fire for otherwise-valid placements that just weren't included in the payload.

**The solver's request/response schemas (`solver/app/schemas.py`) need matching additions.** `VisitIn` gains `interval_days: int | None`, `previous_visit_id: int | None`, `previous_actual_date: date | None` (the three new per-visit facts above); `requested_date` stays but its meaning shifts (nominal anchor, not the date to schedule on). `ScheduledVisitOut` currently has no date field at all (`visit_id`, `employee_id`, `start_minutes`, `end_minutes`) - it implicitly relied on the caller already knowing each visit's (fixed) date. It gains a `date: date` field so the response reports which date the solver actually chose per visit.

**`days_until_due` is unaffected; `requested_date` in the payload is no longer floored to today.** `_visit_payload`'s `requested_date` field changes from `effective_schedule_date(visit).isoformat()` to `visit.requested_date.isoformat()` (the true, possibly-past nominal date) - it's now purely the preference anchor, not a value the solver is required to land on. `days_until_due` keeps its current formula (`effective_schedule_date(visit) - today`, floored at 0) unchanged, per the Non-Goals above.

## Risks / Trade-offs

**The nominal-date-vs-interval weight ratio is a genuine tuning question, not a one-shot correctness decision.** → Start with a conservative, clearly-documented constant (matching how `_TIME_WEIGHT_PER_MINUTE` and `_unscheduled_priority_weight`'s tier constants are already documented in `constraints.py`), verify it reproduces the worked example from the design discussion, and treat further tuning as expected follow-up once real scheduling results are visible - not a blocker to shipping this change.

**Search space grows, and this measurably degrades solve quality at realistic data volumes.** Every visit now has a `date` choice multiplying its `employee` × `start_minutes` choices by up to `days_ahead` values. Verified against a realistic dev dataset (~150 visits, 3 employees, heavily oversubscribed on day 1 - the exact shape the original bug report described): at the old flat 30s budget, going from `days_ahead=1` to `days_ahead=7` scheduled *fewer* visits than the single-day baseline (13 → 7) and produced zero spread to later days at all. Even a generous 180s budget only reached 19 scheduled with a single visit spread to day 2 - the construction heuristic front-loads everything onto day 1 and local search doesn't reliably escape that local optimum within a practical synchronous-request time budget at this scale.

→ Mitigation shipped with this change: `backend/app/solver_client.py`'s `_default_time_limit_seconds(window_days)` scales the solver's default time budget with the window size (`30 + 10 * (window_days - 1)`, capped at 90s) whenever the caller doesn't explicitly set `time_limit_seconds`. This recovers *some* quality (at `days_ahead=7`, scheduled count rose from 7 to 10 against the 13-visit single-day baseline) but does **not** fully resolve the regression - even at the 90s cap, the dataset above still showed no spread to later days. Full resolution (a better construction heuristic / custom move selector, and/or a lower visit-count threshold for mandatory `parallel` region-splitting) is explicitly out of scope here and deferred to a follow-up change.

**Every "same day" constraint needs its joiner updated from `requested_date` to `date` in the same change** - missing even one would silently reintroduce double-booking or driving-time-gap bugs for visits placed on different days than their nominal one. → `constraints.py` already centralizes these as shared module-level joiner lists (`_same_employee_same_date` etc.) rather than inlining them per-constraint, so there's exactly one place per joiner to update, not N call sites; tasks.md accounts for each one explicitly.

## Migration Plan

- No database schema change - `interval_days`/`previous_visit_id`/`previous_actual_date`/`date` are solver-payload-only fields, computed at request time, never persisted.
- No change to `backend/app/main.py`'s response handling: the solver's response shape (`scheduled`/`unscheduled_visit_ids`) is unchanged; only how `planned_start`'s *date* gets chosen changes, from a fixed input to a solver decision reflected in the response the same way `start_minutes` already is. (`main.py` currently reconstructs `planned_start` from `effective_schedule_date(visit)` + the solver's `start_minutes` - this needs to instead use whatever date the solver's response reports for that visit, which is itself a small, contained change to that reconstruction, not a new capability.)
- Deployment: no new dependency, no migration step; a plain code deploy of `solver/` and `backend/`.
