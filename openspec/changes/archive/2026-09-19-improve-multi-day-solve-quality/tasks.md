- [x] 1.2 Run the full existing solver test suite (`solver/tests/`) and confirm nothing implicitly depended on the old 1-second cutoff's timing or score characteristics; if something did, fix that test's assumption, don't revert the bug fix
- [x] 1.3 **Added scope, discovered live during this change's implementation (user-reported crash), not in the original proposal**: `solve_schedule` called `SolverFactory.create(solver_config)` fresh on every request, which JIT-compiles the constraint provider via JPype/jpyinterpreter - not thread-safe. Two concurrent `/optimize` requests (exactly what `parallel` mode, and now this change's mandatory-split mitigation, produce) race on that compilation and corrupt it, observed live as `ClassNotFoundException`/`TypeError: No matching overloads found for ...penalizeLong(...)` on otherwise-correct constraint code. Reproduced directly (4 concurrent `solve_schedule()` calls, 3/4 failed) and fixed by building a single process-wide `SolverFactory` once (lock-guarded) and reusing it via `build_solver(SolverConfigOverride(termination_config=...))` per request instead of rebuilding the whole config/factory each time - confirmed the same reproduction now succeeds 4/4, and the full solver test suite (31 tests) still passes
- [x] 1.4 This bug was already reachable before this change (`parallel` mode already existed) but far more likely to be *hit* once this change's mandatory-split threshold makes concurrent group solves routine rather than opt-in - noting that connection here rather than treating it as unrelated
