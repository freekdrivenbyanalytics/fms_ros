# Design

## Context

`add-multi-day-scheduling-window` (archived) added a `date` planning variable to `VisitAssignment` so the solver can place a visit on any date within the run's window, not just its own nominal date. Its own manual verification (task 8.7) found that at realistic data volume (~150 candidate visits, 3 employees) solve quality degrades badly as `days_ahead` grows, and shipped a partial mitigation (`_default_time_limit_seconds`, scaling the default time budget with window size, capped at 90s) while explicitly deferring full resolution to a follow-up - this change.

That change's design.md attributed the degradation to "local search not escaping the day-1 pileup." Direct investigation for this change found a more specific and more actionable cause. Re-running the exact real-data payload through a hand-built solver config with Timefold's own diagnostics enabled showed:

```
DefaultConstructionHeuristicPhase terminated early with step count (9).
The solution may not be fully initialized.
```

at `days_ahead=7`, `time_limit_seconds=30` - the **construction heuristic phase itself never finishes** initializing the problem; local search (where the day-1-pileup story would apply) barely runs at all. The same payload at `days_ahead=1` (single date, i.e. this problem's shape before the archived change) reaches 28 steps in the same 30s - construction heuristic was already marginal at this data volume *before* the multi-day change, and the new `date` variable's extra candidate dimension (roughly tripling the per-step candidate space at `days_ahead=7`) made an existing scalability ceiling worse, not introduced a new one from nothing.

Separately, `solver/app/solve.py`'s termination config has a definite bug:

```python
unimproved_seconds = min(1, time_limit_seconds)
```

Since `time_limit_seconds` is always >= 1, this evaluates to exactly 1 second regardless of the configured budget - local search (on the rare occasions it gets meaningfully invoked) gives up after 1 second without an improving move, no matter how large `time_limit_seconds` is. The comment above it describes the intended behavior correctly ("small problems finish quickly... `spent_limit` still bounds worst-case runtime for larger ones") but the formula doesn't implement that intent - it should grow with the budget, not shrink to a constant.

The archived change's own manual verification (task 8.5) already showed that splitting a large run into independent per-region groups avoids this entirely: two disjoint groups of 62 and 29 visits (real data, real employees) each fully solved and spread cleanly across the window in well under 30s - because each group is a small enough problem for construction heuristic to actually finish.

## Goals / Non-Goals

**Goals:**
- Bring solve quality at realistic data volume back to at least the old single-day baseline (or better) for `days_ahead > 1`, without requiring the caller to already know to ask for `parallel` mode.
- Fix the `unimproved_spent_limit` bug so local search's actual behavior matches the documented intent.
- Fix the concurrent-solve JIT-compilation race discovered live during this change's implementation (see Decisions) - a correctness bug, not a quality one, but directly implicated by this change making concurrent group solves routine.
- Preserve `parallel` mode's existing no-double-booking guarantee when splitting is triggered automatically, not just when explicitly requested.
- Leave a documented, evidence-based starting point for the split threshold and the local-search patience constant, both flagged as tuning questions to revisit with real usage data - not one-shot correctness decisions.

**Non-Goals:**
- Guaranteeing optimal or near-optimal schedules - this change targets "spreads visits across the window and schedules close to what the data can support," not a formal optimality bound.
- Solving arbitrarily large datasets (thousands of visits) in real time. If real data grows well past what's been tested here, this change's threshold and constants will need retuning, or a more fundamental algorithmic change - out of scope now.
- Changing the constraint model itself (weights, hard constraints, the nominal-date/interval preferences) - this change is about solver execution strategy and configuration, not the scoring rules from the archived change.
- A conclusive fix for construction-heuristic per-step cost. The investigation task in this change is exploratory; if no viable configuration improvement is found, mandatory region-splitting is the change's actual deliverable and that's an acceptable outcome.

## Decisions

**Fix `unimproved_spent_limit` to scale with the configured time budget, not a flat 1 second.** Replace `min(1, time_limit_seconds)` with a value that grows with `time_limit_seconds` (e.g. `max(5, time_limit_seconds // 3)` - exact constants are a tuning question, same posture as the archived change's nominal-date/interval weight ratio: start conservative, document the reasoning inline, and treat further tuning as expected follow-up once real results are visible). This is a definite bug fix independent of which other approach ships - do it regardless.

**Build `SolverFactory` once and reuse it, instead of rebuilding it (and racing on JIT compilation) per request - discovered live during implementation, not in the original proposal.** While implementing this change, the user hit a live crash running `parallel` mode with a 180s time limit: `TypeError: No matching overloads found for ...penalizeLong(...)` inside `define_constraints`, on constraint code that is otherwise correct and fully covered by passing unit tests. Root cause: `solve_schedule` called `SolverFactory.create(solver_config)` fresh on every request; `create()` JIT-compiles the constraint provider and domain classes into JVM bytecode via JPype/jpyinterpreter, which is not safe to run from two threads at once. `parallel` mode's own dispatch (`ThreadPoolExecutor` on the backend, `run_in_threadpool` on each solver request) means two concurrent `/optimize` calls land on the same solver process and race on that compilation - reproduced directly (4 concurrent `solve_schedule()` calls, 3/4 failed with `ClassNotFoundException`/overload-resolution errors that varied run to run, consistent with a genuine race rather than a deterministic bug). The user separately noted their dev startup script runs one solver process, not one per parallel group, which is exactly the topology that exposes this - not a dev-environment quirk, the production topology has the same exposure whenever more than one worker thread serves `/optimize` concurrently.

Fix: build one process-wide `SolverFactory` (no `termination_config` baked in), guarded by a lock so even the very first build can't race, and reuse it via `build_solver(SolverConfigOverride(termination_config=...))` for every request - `SolverConfigOverride` is a Timefold API built exactly for per-solve overrides without rebuilding the factory. Verified: the same 4-concurrent-request reproduction now succeeds 4/4 (including with genuinely different `time_limit_seconds` per call, confirming the override is applied per-request and not shared/leaked across calls), and the full solver test suite (31 tests) still passes.

This is a pre-existing latent bug in `parallel` mode (from the already-archived `add-parallel-region-solving`), not introduced by this change - but this change's mandatory-split threshold makes concurrent group solves the routine case instead of an opt-in one, turning a rare edge case into something a normal `days_ahead=7` run on real data will hit. Fixing it here, not deferring it, since shipping mandatory splitting without this fix would make the system less reliable, not just imperfectly optimized.

**Make region-splitting mandatory above a problem-size threshold, applied even when the caller requests `single` mode.** `backend/app/main.py`'s `propose_optimization` currently only calls `build_parallel_group_payloads` when `options.execution_mode == "parallel"`. Change this to also call it (checking the region graph and falling back to a single solve exactly as `parallel` mode already does when the regions turn out to be fully connected) whenever the run's ready-visit count exceeds a threshold, regardless of the requested mode. This directly and predictably shrinks problem size to something construction heuristic can finish - the only lever validated so far by real measurement (8.5's two-group split), rather than something that needs further research to confirm works at all.
- *Where to measure the threshold*: total `ready_visits` count for the run (post skill/region/window filtering, pre-split) - this is what actually drives per-solve construction-heuristic cost, not `days_ahead` or employee count directly.
- *Starting value*: a conservative default (e.g. 75 ready visits) based on today's evidence - 150 unsplit visits failed badly, ~60-visit split groups succeeded comfortably. Make it a `settings` value, not a hardcoded constant, so it can be adjusted without a code change as real usage patterns become clearer.
- *Alternative considered*: raise `MAX_DAYS_AHEAD` restrictions or shrink the default `days_ahead` instead of splitting. Rejected - the archived change's own data showed the single-day (`days_ahead=1`) case was *already* construction-heuristic-marginal at 150 visits (28/30s steps, not comfortably finishing either); shrinking the window doesn't address the underlying per-solve entity count, and defeats the archived change's whole purpose.
- *Alternative considered*: only ever split when `parallel` is explicitly requested, and instead just document "ask for `parallel` mode on large runs." Rejected - the caller (the frontend, or any API consumer) has no way to know in advance whether a run is "large" without duplicating this same threshold logic client-side; the backend already has the visit count by the time it decides how to solve, so it should decide.

**Exploratory: reduce construction heuristic's own per-step cost - investigated, declined for this change.** `SolverConfig`'s Python surface exposes exactly two knobs beyond `environment_mode`/`termination_config`: `nearby_distance_meter_function` (Timefold's purpose-built nearby-selection feature for geography-shaped problems like this one - restricts move/value candidates to those "nearby" an already-placed entity, which is exactly the kind of per-step cost reduction this investigation was looking for) and `move_thread_count` (parallelizes move evaluation across CPU threads). Both were implemented against the real 150-visit payload and both raise `RequiresEnterpriseError` at solver build time - they require `timefold-enterprise`, a paid license, not available in this project's current (community-edition) dependency. No other construction-heuristic/local-search phase configuration is exposed by this binding's Python API (no `ConstructionHeuristicPhaseConfig`/`LocalSearchPhaseConfig` equivalent, and raw XML config (`xml_source_text`) still requires a Python-callable score director that the XML path doesn't obviously support without further investigation this timebox didn't reach). **Declined for this change**: adopting either enterprise feature is a licensing/procurement decision, not an engineering one - flagged to the user as a real, likely-high-leverage option to consider separately, not silently taken on. Splitting (this change's other decision) remains the only viable improvement shipped here.

## Risks / Trade-offs

**The split threshold is picked from one dataset shape (this project's current dev data), not a general formula.** → Document it as a tuning question exactly like the archived change's weight ratio; make it a `settings` value so it's adjustable without a deploy-blocking code change, and flag it for re-evaluation once real production usage patterns exist.

**Splitting cannot help a run whose regions are all connected through shared employees.** Initially measured against this project's *then*-current dev data (employee 4 scoped to two regions, bridging them into one connected group of 91 visits): the 150-visit run only split off a genuinely-unemployed region's visits, leaving the rest as one still-large group. Measured result at that point: 19 scheduled (18 on day 1, 1 on day 2) - a real improvement over the pre-fix baseline (10 scheduled, zero spread) but far short of this change's Goals. The dev data was since updated to one employee per region (no bridging employee), which resolves this for the current project topology - re-measured (task 5.1) at 125/150 scheduled (83%), spread across all 7 days. → No mitigation shipped in this change for the connected-group case itself - it's avoided here by the data topology, not solved in general. If a future employee ever spans multiple regions again (a legitimate real-world case: a cross-region flex employee), this limitation returns for whatever regions that employee bridges. A future change could explore splitting by something other than region (e.g. fixed visit-count chunking with reduced cross-chunk optimality), or the enterprise nearby-selection feature investigated and declined above, if that becomes common enough to matter.

**BREAKING: `single` mode's "entire run solved as one problem" promise no longer holds unconditionally.** → No current caller (frontend or otherwise) is found to depend on that literal guarantee for large runs per this change's Impact analysis; document the new threshold-triggered behavior in the updated spec requirement and in any user-facing release notes.

**The `unimproved_spent_limit` fix changes local search's actual behavior for every existing test and every production run, not just large ones.** → Re-run the full solver test suite after the fix (not just the tests touching this file) to catch any test that implicitly depended on the old 1-second cutoff's timing or score characteristics.
